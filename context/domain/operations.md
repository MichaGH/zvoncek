# Operations

Reusable server code that exists **today**. Reference, not tutorial: what it does, what it guards, what it bumps.
If you need one of these behaviours, call it — do not re-implement it. Adding or removing one? Update this file in the
same change. Anything marked **unused** exists but has no caller; do not build on it without reading its note.

Layer meaning: `access` = guard/lock helper · `command` = transaction body taking an `AccessUser` · `domain` = pure rule
or shared mutation body · `query` = scoped read.

## Access / locking (`lib/access/`)

| Operation | Notes |
|---|---|
| `requireUser()` | current **DB** user (`deletedAt: null`) as `AccessUser`, not `session.user`. Returns `null` when logged out or deactivated; the caller redirects (`/login?deactivated=1`). |
| `withLockTx(fn, { lockTimeout?, timeout? })` | interactive transaction with `SET LOCAL lock_timeout` (default `5s`); deadlock / lock timeout become `RETRYABLE` via `toActionError`. |
| `lockUsers(tx, ids, "SHARE" \| "UPDATE")` | locks user rows one by one, ascending id; returns found users (deactivated included). |
| `lockUserModes(tx, [{ id, mode }])`, `lockTeams(tx, ids, mode)` | mixed modes in one ascending pass / team rows. Lock order `Team → User → Lead`. |
| `lockLeadRow(tx, id)` | `SELECT … FOR UPDATE`; `false` when the row is gone. |
| `lockLeadWithUsers(tx, leadId, userIds, { expectedRevision })` | reads `assignedCallerId` without a lock, locks those users `FOR SHARE`, locks the lead, re-validates that the assignee did not change; `STALE` on revision mismatch. Used by the deal guards. |
| `requireCallLead(tx, user, leadId, expectedRevision?)` | call-stage mutation guard: `calls.work`, lead in the call stage **and** assigned to the actor, else `NOT_ASSIGNED`. |
| `requireDealWork(tx, user, leadId, { expectedRevision, closedPolicy, lockUserIds })` | deal mutation guard for **owner or manager**; not in scope ⇒ `NOT_FOUND`. `closedPolicy`: `reject` (default, closed ⇒ `DEAL_CLOSED`) / `allow` (manager only). Returns `{ lead, actor, users, isManager }`. |
| `requireDealManage(tx, user, leadId, { expectedRevision, lockUserIds })` | manager-only guard (`deals.manage`), any deal state; non-manager ⇒ `NOT_FOUND`. |
| `requireDealView(db, user, leadId)` | **unused** since the round-2 merge. Round-1 read guard; it ignores `deals.viewTeam`. Do not use it — `getDealDetail` enforces scope inside its query. |
| `isOpenDealStatus`, `isClosedDealStatus` | `ACTIVE`/`SNOOZED` vs `WON`/`LOST`/`UNREACHABLE`. |
| `AccessError(code, message?)`, `toActionError(err, fallback, label)`, `UNAUTHENTICATED`, `FORBIDDEN`, `isUniqueViolation`, `isRetryableDbError` | error plumbing. Wave 3 codes: `STEP_LOCKED` (the step is locked by an open task), `TASK_OVERLAP` (a send overlaps a part the manager is still making — choose `KEEP_OPEN` / `WITHDRAW_PARTS`), `RESULT_PENDING` (I10). Codes and the client's reaction: `context/architecture.md` §4. |

## Commands (`lib/commands/`)

| Operation | Guard / effect |
|---|---|
| `claimBatchAs(user)` (`claims.ts`) | claims up to `CLAIM_BATCH_SIZE` pool contacts (`SKIP LOCKED`), sets `assignedCaller*`. |
| `logCallAs(user, input)` (`calls.ts`) | first call: `requireCallLead` + revision + idempotency; writes the `CALL` activity then stores `leadRevision`, applies `leadStateForOutcome`, performs the handoff (`resolveDealOwner`, `pipelineEnteredAt`, `handedOffById`) and writes `DealOwnership(HANDOFF)`. Replays on a lost race. **Wave 5:** `outcome: "INTERESTED"` takes a non-empty `asked: RequestContent[]`, writes one `LeadRequest` per tick plus `meta.asked` / `meta.fp` (the same key with a different selection is `IDEMPOTENCY_CONFLICT`), and derives the whole step from the ticks. The legacy `WANTS_*` outcomes are still accepted and create no rows. |
| `updateLeadContactAs(user, leadId, patch)` (`calls.ts`) | caller edits contact data in the call stage. |
| `revertCallResultAs(user, activityId, expectedRevision)` (`history.ts`) | undoes a first-call result only if `Activity.leadRevision == Lead.revision`; also undoes the handoff (`DealOwnership(REVERT)`). Audit `CALL_REVERTED`. |
| `transferCallWorkAs(actor, { fromUserId, toUserId, kind, limit })`, `releaseBatchAs(actor, fromUserId)` (`assignments.ts`) | `calls.assign`: move call work between users or back to the pool (`toUserId: null`); never skips rows. |

| `logFollowUpAs(user, input)` (`dealWork.ts`) | the interaction: strict input, `requireDealWork` + revision + full fingerprint via `runKeyed`. `contact` decides the history row: `CALL` → `CALL`, `REPLIED` → `CLIENT_REPLIED`, `SMS` → `SMS_SENT`, `NONE` → no contact row (the key sits on the planning row). Applies `dealStateForFollowUp`, plans the step (`stepNote` separate from the contact note). **While a task is open**: only a fact (`keepLockedStep`) — any step / status input is refused — or, owner only, `cancelTask {taskId, reason}` + a new step / snooze / close in the same transaction. `overlap` answers `TASK_OVERLAP` for a phone price (`WITHDRAW_PARTS` + `withdrawParts` takes back just the price part; `cancelTask` stays the whole-task input used by snooze / close / replan); `fulfils` / `dismiss` consume returned items. `phonePrice` writes an `OFFER_SENT` channel `PHONE` linked to the call. **Wave 5:** `asked` ("Chcú aj …", only with a real client contact) adds request rows — also while the step is locked, because it is a fact about the client; a price told in the same call resolves that call's PRICE rows **by link**; when the user submitted no `nextKind` and the resulting step is one the app chose itself, the step is re-derived from the outstanding work (§6.8). `stepFromRequests` (only with `asked`, outcome `POSITIVE`, no `nextKind` / `schedule`) makes the server derive the step from what is still outstanding **after** the asks and the same-call phone price are written; nothing outstanding → `STALE` (the sheet then asks "Kedy ďalej?"). `withdraw {ids, reason}` (only with outcome `SNOOZE` / `NOT_INTERESTED` / `BAD_NUMBER`): when the deal has open client requests it is **required**, the ids must equal exactly the open rows now (else `STALE`), the reason is non-empty, and the rows are withdrawn under the same lock with a `CLIENT_ASK_CHANGED` audit row (`meta.via`). The check + withdrawal is the shared `withdrawOpenOnLeave` (`requestMutations.ts`); the manager's `changeStatusAs` / `markLostAs` (LOST / UNREACHABLE only; WON refuses it) use the same helper through `closeDeal`. `phonePrice` is also accepted with `contact: "SMS"` (stored as channel `PHONE`, `via: "SMS"`). Correcting an `SMS_SENT` (`correctRecordAs`) also crosses out the `OFFER_SENT` whose `meta.callActivityId` is that SMS, in the same transaction. `changeStatusAs` accepts `withdraw` for `SNOOZED` / `LOST` / `UNREACHABLE` (required when asks are open) and refuses it for other statuses. `keepStep` (only with `contact: "SMS"`, no `nextKind` / `schedule` / `stepNote`) writes the SMS as a fact and leaves step and status untouched — the same fact-only path as a locked step, without needing a task. `sourceFor(user)` is exported. |
| `updateDealContactAs`, `saveDealQuoteAs` (`dealWork.ts`) | owner-or-manager deal work, open deals only for the owner. Activity source follows the actor. |
| `setDealNextActionAs`, `addDealNoteAs` (`dealWork.ts`) | **no UI caller since wave 3b**; kept, used by the check scripts. `setDealNextActionAs` refuses a locked step. |
| `setClientAsksAs(user, input)` (`requests.ts`) | wave 5, the pencil at "Chceli": `add: RequestContent[]` and `withdraw: string[]` (**ids of OPEN rows of that lead**; a `SENT` / `WITHDRAWN` row returns `STALE`). A reason is required only when something is withdrawn. Guard `requireDealWork` (owner or manager; an ownerless deal is manager-only; out of scope `NOT_FOUND`; closed deal `DEAL_CLOSED`), keyed `CLIENT_ASK_CHANGED` main row with `meta.added` / `meta.withdrawn` (ids **and** contents) / `meta.reason` / `fp`, one revision bump. It never cancels an open task. With an open task it calls `refreshLockedStep` (P6, no `isSystemStep` guard); without one it re-derives the step only when the app chose the current one. |
| `recordOfferSentAs(user, input)` (`offers.ts`) | "Čo sme poslali": strict input (`contents` — incl. `REVIEW`, `sentOn` ≤ today, optional `price`, `designIds` **or** `untrackedDesign` (a návrh with no `Design` row — refused when the deal has any non-deleted `Design`, never with ids, never with a returned-návrh `fulfils`; stored as `meta.untrackedDesign`, moves no `Design.sentAt`, drives `Lead.designSentAt` for a deal without designs), `followUp` + `followUpOn`, `historical`, `fulfils`, `dismiss`, `overlap`, `withdrawParts`), `requireDealWork` + `expectedRevision` + full fingerprint. While a task is open the send is a fact only and the locked step is re-derived from what is left (`refreshLockedStep`); a send covering a kind the manager is **still making** needs `overlap`; `withdrawParts {taskId, kinds, reason}` is accepted **only** with `overlap: WITHDRAW_PARTS` and a non-empty reason (owner only) and takes back exactly those parts — the rest of the task runs on, and the task closes (and the step unlocks) only if nothing is left. Dismissals need `assertDecidesResults`. `historical` = manager only, only on an unreviewed legacy deal, never `followUp`, never `fulfils`. |
| `correctRecordAs(user, activityId, reason)` (`offers.ts`) | crosses out an `OFFER_SENT` / `SMS_SENT` / `CLIENT_REPLIED`: its author or the manager, reason 3–500 chars; already crossed out → `STALE`; any other type → `FORBIDDEN`. |
| `confirmLegacyReviewedAs(user, leadId)` (`offers.ts`) | manager only (`requireDealManage`): sets `legacySendsReviewedAt` on a `hadLegacySends` lead + audit row. |
| `askManagerAs(user, input)` (`tasks.ts`) | the owner-rep creates a `HELP` (**1–3 `contents`**, one part each — wave 4) or `HANDOVER` task for a resolver (`assigneeId`). One open task per deal (`STALE`); duplicate kinds refused. The locked step is derived (`stepAfterTask`) and the step the deal had **before** is stored as the task's fallback; `step` is only accepted for "Iné" (any I10-allowed kind) or when it equals the derived kind. Wakes a snoozed deal. Key `TASK_CREATED`. |
| `taskMessageAs` (`tasks.ts`) | internal message on the open task (owner or manager); never a client contact. Key `TASK_MESSAGE`. |
| `resolveTaskPartsAs` (`tasks.ts`) | resolver: deliver and/or decline **named parts** of one `HELP` task in one save (`parts: [{ kind, op: "DELIVER", price? / designs? / answer? } \| { kind, op: "DECLINE", reason }]`). A delivered `PRICE` is also saved as the deal's price (`via: "TASK"`); values for a kind that was not named are `FORBIDDEN`. The task closes only when nothing is left `REQUESTED`; otherwise the step stays locked and follows what is left. Key `TASK_PART_DONE` when anything was delivered, else `TASK_PART_DECLINED` (the replay lookup passes **both**). Replaces `finishTaskAs` and absorbs the old `declineTaskAs`. |
| `finishAndSendAs` (`tasks.ts`) | resolver did it and sent it himself: the same `parts` + `OFFER_SENT` (with `fulfils` for exactly those items) + the recomputed task status, one transaction. "Zavolať, či prišlo" is planned **only** when this save closes the task *and* nothing is outstanding afterwards; otherwise the step becomes the remaining send. While a part is still being made the send is a fact only and the step stays locked. |
| `withdrawTaskPartsAs` (`tasks.ts`) | **owner only**: takes named `REQUESTED` parts back with a reason ("Už netreba"). A `DELIVERED` part cannot be withdrawn — "Neposielam" is that path. A chosen `step` is accepted only when the withdrawal closes the task **and** nothing is outstanding. Key `TASK_PART_WITHDRAWN`. |
| `addTaskPartsAs` (`tasks.ts`) | **owner only**: adds a kind to an open `HELP` task with a required message (the manager reads it in the thread). A kind already `REQUESTED` / `DELIVERED` / `DECLINED` is refused; a `WITHDRAWN` one returns to `REQUESTED`. Key `TASK_PART_ADDED`. |
| `declineHandoverAs`, `reassignTaskAs` (`tasks.ts`) | resolver: refuses a `HANDOVER` with a reason ("Nie, pokračuj ty" — the client stays with the rep, the step unlocks) / moves the task to another resolver (not the owner). A `HELP` task is declined **by parts**, not whole. |
| `dismissResultsAs` (`tasks.ts`) | "Neposielam" (price / návrh, reason required) / "Beriem na vedomie" (answer, decline); the owner decides, on an ownerless deal a manager. |
| `takeoverAs` (`tasks.ts`) | manager (`deals.manage` + `deals.receive`) takes the client over with his own step; an open `HANDOVER` becomes `DONE`, a `HELP` is cancelled. Via `ownerTransition`. |
| `updateLeadAs`, `saveQuoteAs`, `setProjectTypeAs` (`pipeline.ts`) | manager-only (`requireDealManage`), any deal state. `setNextActionAs` and `addBusinessNoteAs` (`NOTE` only) have **no UI caller since wave 3b**. |
| `changeStatusAs(user, leadId, { status, expectedRevision, idempotencyKey, cancelTask?, withdraw?, snoozeUntil? })` (`snoozeUntil` = future business day; **required** when a snooze cancels an open task, and must be after today; the cancelled task ends through `stepOnTaskClose`, then the date is overwritten), `markLostAs(…, { reason, …, cancelTask? })`, `reopenDealAs(…, { expectedRevision, idempotencyKey })` (`pipeline.ts`) | manager-only, keyed (`runKeyed`). Reopen (also via the status select) locks the retained owner before the Lead and hands an ineligible owner's deal to the reopening manager (`OWNER_CHANGED` + `DealOwnership(CHANGE)`). An open task blocks a status change unless `cancelTask` names it; closing dismisses pending items. |
| `changeOwnerAs(user, leadId, { ownerId, expectedRevision, idempotencyKey, taskAssigneeId? })` (`pipeline.ts`) | manager-only, keyed; through `ownerTransition` (to a rep the task stays, optionally to another manager). |
| `transferDealsAs(user, { operationId, fromOwnerId, handedOffById?, statuses?, toOwnerId, taskAssigneeId?, limit? })` (`pipeline.ts`) | bulk owner transfer in batches of 200 (cursor, sorted user locks, `FOR UPDATE SKIP LOCKED`, re-read and skip on change), each deal via `ownerTransition`; returns `{ moved, skipped }`. A repeat with the same `operationId` + `bulkFp` continues. |
| `deleteTeamAs`, `setTeamLeaderAs`, `setUserTeamAs` (`teams.ts`) | lock `Team` before `User`. Team **create** and **rename** have no command — `createTeam` / `renameTeam` write directly in `lib/actions/teams`. |
| `createDesignAs`, `addDesignVersionAs`, `updateDesignMetaAs`, `removeDesignAs` (`tracking.ts`) | guarded through `design.leadId` with `requireDealManage`. `removeDesignAs` recomputes the lead's send summary (`recomputeOffers`). Marking a design sent is `recordOfferSentAs` with `DESIGN`. Tracking ingest (`app/api/p`) never bumps the revision. |

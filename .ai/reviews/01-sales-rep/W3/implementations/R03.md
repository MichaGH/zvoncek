# Wave 3 implementation review — R03

Date: 2026-09-19  
Scope: verification of the R02 fixes, a final Wave 3 implementation pass, and compatibility with the planned combined PRICE + DESIGN task and partial delivery described in `context/features/01-salesrep/wave-4-proposal.md` §2.  
Review type: implementation review (read-only apart from this review record). No database command was run.

## Verdict

**Changes requested.** The four actionable R02 code/documentation findings are fixed correctly; the deleted backup directory is intentional and is not a finding in this round. The existing Wave 3 architecture is a sound base for a combined task: `DealTask.contents[]`, item-addressed `fulfils`, one open task per deal, and the step lock do not require a replacement table or a new `NextActionKind`.

One current Wave 3 bug remains: when both a returned návrh and price are pending and the návrh is sent first, sending the final price defaults to keeping `SEND_DESIGN`, even though nothing remains to send. The Wave 4 draft also needs a firmer item-state contract before partial delivery is implemented. In particular, a partial result must survive decline/cancellation/takeover, and the existing whole-task overlap choice is unsafe for a combined task.

The combined/partial feature itself is **not implemented yet**. The repository says this explicitly in `wave-4-proposal.md:3-5`; the current code only contains preparation points and `[WAVE 4]` markers. This review therefore distinguishes an existing Wave 3 defect from design gaps that must be resolved before Wave 4 code is written.

## Findings

### 1. IMPORTANT — sending the final returned price can leave a false `SEND_DESIGN` step

**Where**

- `components/pipeline/OfferSentDialog.tsx:137-145` decides that a send completes the step by comparing the stored step kind with the contents of this send.
- `components/pipeline/OfferSentDialog.tsx:454-469` consequently defaults to “Ponechať: Poslať návrh” when the final send contains only PRICE.
- `lib/domain/tasks.ts:201-206` deliberately permits `SEND_DESIGN` while only a PRICE item remains, because a návrh email can carry the price.
- `context/features/01-salesrep/wave-4-proposal.md:94-96` explicitly promises that partial completion works in either order.

**Concrete failure scenario**

1. A deal has returned PRICE and DESIGN items and the stored step is `SEND_DESIGN`.
2. The SR sends only the návrh first. The price correctly remains pending, so the step stays `SEND_DESIGN`.
3. The SR later opens “Čo sme poslali” and sends the returned price. This send consumes the last pending item.
4. `completesStep` is false because the stored kind is `SEND_DESIGN` and this send has no design. The dialog defaults to “Ponechať: Poslať návrh”.
5. Saving the default consumes the final price but leaves a due `SEND_DESIGN` step even though no návrh or price remains pending.

This is already reachable in Wave 3 by completing a price task, then a design task before sending the price, and sending the two returned items separately. It will become a normal path once combined tasks may be fulfilled in either order.

**Why it matters**

The deal returns to the actionable pipeline with an instruction that is no longer true. A rep can resend something unnecessarily or must manually repair the step. It also makes the “návrh first, then price” half of the proposed symmetric workflow fail.

**Suggested fix**

Determine step completion from the returned-item state **after this save**, not only from `nextActionKind` versus the current email contents. If there is no open task and this send/dismissal consumes the last pending PRICE/DESIGN item that constrained the step, default to—and preferably require—the follow-up call just as when the matching raw step kind is sent. Add tests for both orders:

- price sent first, návrh last → CALL;
- návrh sent first, price last → CALL;
- leaving either item pending → the send step remains.

### 2. BLOCKER — partial results have no defined survival rule when the open task ends without normal completion

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:87-96` says an OPEN task may contain a delivered result and tests only normal completion plus decline.
- `lib/domain/tasks.ts:165-188` currently returns items only from DONE/DECLINED tasks, and a DECLINED task emits the decline item and immediately skips its result.
- `lib/domain/taskMutations.ts:62-80` currently loads only DONE/DECLINED tasks for pending-item calculation.
- `lib/domain/dealMutations.ts:267-284` cancels an open task before loading and dismissing pending results when a deal closes.
- `lib/domain/taskMutations.ts:523-549` can cancel an open HELP task during unassignment or manager takeover.

**Concrete failure scenario**

1. A combined PRICE + DESIGN task is OPEN.
2. The manager partially delivers the price. It appears as a pending returned item.
3. Before the design is ready, one of these happens: the manager declines the remaining design, the owner cancels the task, the deal closes, the deal is moved to nobody, or a manager takes it over.
4. Under the current status-based item rules, DECLINED short-circuits to only a decline item and CANCELLED is excluded completely. The already delivered price disappears from the returned-item ledger without being sent or explicitly dismissed.
5. On close, cancellation happens before `dismissAllPending`; a future query that only includes OPEN/DONE partial results would stop seeing the price before it can write the required dismissal history.

**Why it matters**

This breaks the central Wave 3 invariant that a returned result cannot be silently forgotten. It is a data-integrity problem, not a display preference.

**Suggested fix**

Define returned items independently from the task's final status: any valid part present in `DealTask.result` remains a returned item in OPEN, DONE, DECLINED, and CANCELLED states until an `OFFER_SENT` or `TASK_RESULT_DISMISSED` consumes it. DECLINED adds a separate DECLINED item; it must not replace already delivered parts. Ensure close/cancel/takeover either dismisses those items before changing visibility or uses a query that still sees partial results after the status change.

Add explicit tests for partial price followed by: decline, owner cancellation, closing WON/LOST, unassigning, manager takeover, transfer to another rep, and reassignment to another resolver.

### 3. IMPORTANT — the existing overlap choice can cancel the unfinished half of a combined task

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:61-64` says combined-task overlap needs no change.
- `lib/domain/tasks.ts:218-225` considers overlap against the task's original `contents`, not the parts the manager still has to produce.
- `components/pipeline/OfferSentDialog.tsx:398-425` offers “Už to netreba – zrušiť úlohu”, which cancels the whole task.
- `lib/commands/offers.ts:99-110` implements that selection as whole-task cancellation.

**Concrete failure scenario**

The manager has already returned the price for a PRICE + DESIGN task and is still making the design. The SR sends that returned price. Because PRICE remains in the task's original `contents`, the dialog says the manager is currently making what the SR is sending and offers to cancel the task. Choosing cancellation ends the entire task, including the still-needed design.

The same ambiguity exists if the SR independently obtains a price while both parts are outstanding: “price no longer needed” does not mean “design no longer needed”.

**Why it matters**

A normal option in the exact requested edge case can silently stop the manager's remaining work. The current whole-task choice is safe only because today's UI creates single-content tasks.

**Suggested fix**

Overlap must use **outstanding manager work**, not original task contents. Sending a part the manager already delivered is fulfilment, not overlap, and should simply keep the task open for the remaining part. If the SR independently supplies a still-outstanding part, either:

- support an audited per-part withdrawal and keep the other part open; or
- for Wave 4, allow only “keep task open” for partial overlap and reserve whole-task cancellation for an explicit separate action.

Do not reuse `CANCEL_TASK` as “cancel this one part”. Add server tests proving that sending/withdrawing PRICE cannot close an outstanding DESIGN part and vice versa.

### 4. IMPORTANT — the proposal lacks a canonical part-state and audit/idempotency contract

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:73-76` proposes `stepLabel(kind, openTask, pending)`.
- `context/features/01-salesrep/wave-4-proposal.md:87-93` says partial output is written into `DealTask.result` and a `TASK_PART_DONE` activity records each part, but does not define its metadata, fingerprint, merge rules, or retry behavior.
- `prisma/schema.prisma:429-433` and `context/domain/database-map.md:169-171` currently define task-level `closedBy`, `closedAt`, and an immutable result snapshot.
- `lib/domain/tasks.ts:156-188` attributes every returned item using the task's `closedBy`/`closedAt`; an OPEN task has neither.
- `lib/queries/pipeline/index.ts:186-199,298-340,714-729` does not include an open task's result in list/open-task views.

**Concrete failure scenario**

Manager A returns the price on Monday; the task remains open. Manager B is later assigned and returns the design on Friday. The UI promised “Cena ✓ (hotové 19. 9.)”, but the current item model can only show the task's eventual closer and final `closedAt`, so it cannot truthfully attribute or date the price. Two tabs can also submit the same part or different versions of it unless the new command has the same keyed/fingerprinted transaction contract as every other Wave 3 mutation.

`stepLabel(kind, openTask, pending)` is also insufficient as written. After a delivered price has already been sent, `pending` no longer contains it while `openTask.contents` still does; without the open result and consumption state, the helper cannot tell whether price is unfinished, delivered-but-unsent, or already sent.

**Why it matters**

Without one canonical state, the task card, row label, overlap logic, send dialog, and server validation will derive different answers. Mutable JSON without defined merge/retry rules risks overwriting a previously delivered part.

**Suggested fix**

Define one pure `TaskPartState` projection with, for every requested part:

- requested;
- still being produced;
- delivered, including immutable snapshot, actor and time;
- pending delivery to the client;
- consumed/dismissed.

Derive it from `DealTask.contents`, the merged result, `TASK_PART_DONE`/`TASK_DONE`, valid `OFFER_SENT.fulfils`, and dismissals. Use it for labels, ticks, overlap, and command validation. The partial command must carry `expectedRevision` and an idempotency key; `TASK_PART_DONE` should be its keyed primary row with a canonical fingerprint containing the exact delivered parts and snapshots. Under the Lead lock, merge only previously undelivered parts, reject attempts to overwrite a returned part, bump once, and close with `TASK_DONE` only when every requested part exists. Record actor/time per part in the part event, rather than pretending the task-level close fields describe it.

### 5. IMPORTANT — the proposed first-call outcome cannot currently preselect both task contents

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:98-103` promises that “Chcú cenu aj návrh” enters the pipeline and later pre-ticks both in the manager-request dialog.
- `components/pipeline/AskManagerDialog.tsx:27-35,83-96` receives only the stored step and pending items; `SEND_DESIGN` preselects DESIGN only.
- `lib/domain/leadFlow.ts:113-148` shows that first-call intent is currently collapsed into a generic step kind.
- The user's intended next feature introduces a richer “client asked for” selection; `wave-4-proposal.md:28-32` currently postpones that redesign to Wave 5.

**Concrete failure scenario**

Telesales records “client wants price and návrh”. The proposed flow stores a `WANTS_PRICE_AND_DESIGN` activity but maps the lead to the same `SEND_DESIGN` step used for “návrh only”. When the SR later opens “Požiadať manažéra”, the dialog sees only `SEND_DESIGN` and preselects DESIGN. It cannot know that PRICE was also explicitly requested.

**Why it matters**

The promised automation loses exactly the distinction the new feature is meant to preserve. Inferring client intent from the current next step is unsafe because the step is an action, can be changed, and is shared by several workflows.

**Suggested fix**

Decide the boundary before implementation:

- preferably build the new canonical “client asked for” contents first and let the task dialog prefill from it; or
- as a temporary Wave 4 bridge, explicitly query and pass the authoritative first-call outcome into `AskTarget` and document when that suggestion stops applying.

Do not infer “asked for both” from `SEND_DESIGN` or from whichever activity happens to be latest. Also update the wave numbering: the current draft says the selector redesign is Wave 5, while the current product decision says it belongs to the next feature wave.

### 6. IMPORTANT — the proposed implementation order references enum values before applying their schema

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:189-198` proposes `TASK_PART_DONE` and optionally `WANTS_PRICE_AND_DESIGN` as additive enum values.
- `context/features/01-salesrep/wave-4-proposal.md:215-220` puts all Part A code and tests before the schema step.
- `context/code-standards.md:70-74` requires enum values to land before code that writes them.

**Concrete failure scenario**

Part A code imports generated Prisma enums and writes `TASK_PART_DONE` / `WANTS_PRICE_AND_DESIGN`, but the schema/client has not yet gained those values. TypeScript cannot compile cleanly; if code were deployed before the production enum change, PostgreSQL would reject the write.

The readiness table at `wave-4-proposal.md:65` also says the schema change is “one additive ActivityType value; nothing else”, while §6 correctly lists the optional CallOutcome addition too.

**Why it matters**

This is a rollout-order error in a repository whose production database deliberately lags test. The code and schema cannot be safely deployed in the written order.

**Suggested fix**

After the design is approved, apply and verify S-13/S-14 on the test branch first, regenerate Prisma, and only then implement Part A commands/UI/tests. For production, apply additive enum values before deploying code that can write them. Correct the readiness table to list both possible enum additions.

## Recommended combined workflow

No new stored next-step enum and no automatic step rewrite are needed:

1. “Client asked for” records PRICE + DESIGN as two explicit requested contents.
2. The SR creates one HELP task with `contents = [PRICE, DESIGN]`. The stored step is `SEND_DESIGN`, has no date, and is locked. The UI may display “Po vybavení: Poslať návrh + cenu”.
3. The manager returns PRICE only. The task remains OPEN; PRICE gets a truthful part event and a green tick; DESIGN remains outstanding.
4. The SR sends that returned price. The send fulfils the PRICE item. It does **not** cancel or close the task and does not schedule a follow-up while DESIGN is still outstanding.
5. The deal remains in “Čakám na manažéra”, now clearly showing that only DESIGN is being produced. The stored step has not transformed; it is still locked.
6. The manager returns DESIGN. This is the final requested part, so the task becomes DONE and the existing `SEND_DESIGN` step unlocks for today. Because PRICE was already consumed, only DESIGN is pending client delivery.
7. The SR sends DESIGN. The final pending item is consumed and the next step becomes the follow-up CALL.

If both parts are returned before either is sent, the unlocked display can say “Poslať návrh + cenu”; sending both together consumes both and plans the call. If DESIGN is delivered/sent first and PRICE last, the same rule must work symmetrically—finding 1 is the current obstacle.

This keeps the one-next-step model intact. The accepted limitation remains: while the task is still open for DESIGN, the app cannot simultaneously schedule a separate call about the already-sent price. That is a workflow limitation, not a reason to add another task or another `NextActionKind`; if that rare appointment matters, it belongs to the known multi-step/calendar backlog.

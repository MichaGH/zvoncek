# Wave 3 implementation review — R01

Date: 2026-09-19  
Scope: Wave 3 manager tasks, step lock, handover/takeover, returned results, ownership history, list/dashboard integration, rollout documentation.  
Review type: implementation review (read-only apart from this review record). No database command was run.

## Verdict

**Changes requested.** The overall model is coherent and most of the difficult foundations are present: Lead-row locking, revision tracking, keyed retries, task-derived locking, owner transitions, pending-result reconstruction, shared list/count predicates, and the production delta are all implemented in a recognizable and mostly consistent way.

The implementation should not be treated as complete yet. Findings 1–3 are real workflow/data-integrity defects. Finding 4 leaves the approved feature specification and shipped behavior contradictory, so a future implementation agent cannot know which behavior is authoritative. Finding 5 is a smaller server-validation hole.

## Findings

### 1. IMPORTANT — embedded result dismissals bypass the owner-only rule

**Where**

- `context/features/01-salesrep/wave-3-task-proposal-final.md:272-281` — only the current owner may choose “Neposielam” / “Beriem na vedomie”; a manager may do so only when the deal is manager-owned or ownerless.
- `lib/commands/tasks.ts:391-407` — the dedicated `dismissResultsAs` command correctly enforces that rule.
- `lib/commands/offers.ts:87-110` — `recordOfferSentAs` uses the broader owner-or-manager `requireDealWork` guard and then calls `dismissItems` without the owner check.
- `lib/commands/dealWork.ts:186-212` — `logFollowUpAs` has the same omission.
- `lib/domain/taskMutations.ts:129-170` — `dismissItems` validates item existence/reason, but deliberately has no authorization check of its own.
- `components/pipeline/OfferSentDialog.tsx:121-127,183-212` and `components/pipeline/InteractionSheet.tsx:195-209,249-276` — these are reachable normal UI paths, not only forged payloads.

**Concrete failure scenario**

1. Jana owns a deal. Michal finishes an earlier task and returns an `OTHER` answer, or there are two returned prices/design versions still pending.
2. Michal later opens Jana's deal and records a real call. In `InteractionSheet`, acknowledgement of `OTHER`/`DECLINED` is selected by default. The save carries `dismiss`, and the server accepts it because Michal has `deals.manage`.
3. Alternatively, Michal records an offer on Jana's deal. `OfferSentDialog` can include `dropRest`, or it can automatically classify an older returned price/design as superseded. That dismissal is also accepted.
4. A `TASK_RESULT_DISMISSED` row is written and Jana no longer sees that returned item, even though the approved rule and the existing dedicated-command test say that this decision belongs to Jana.

This is especially easy to miss because `prisma/backfill/check-concurrency.ts:2323-2328` proves that the dedicated dismiss command rejects a manager on a rep-owned deal, but does not test the two embedded dismissal paths.

**Why it matters**

Pending task results are part of the deal's workflow state. Consuming them as “not sending” or “acknowledged” changes what the owner sees and relaxes I10. Having the authorization rule only on one of three entry points makes the invariant bypassable through ordinary UI.

**Suggested fix**

Create one shared server-side authorization helper for a returned-result decision and call it before every `dismissItems` invocation that originates from user input (`dismissResultsAs`, `recordOfferSentAs`, and `logFollowUpAs`). Keep system dismissals such as closing a deal separate. Add tests where a manager on an SR-owned deal attempts `dismiss` through both `recordOfferSentAs` and `logFollowUpAs`; both must be `FORBIDDEN`, while an independent factual send/call without `dismiss` must still work.

### 2. IMPORTANT — “finished and sent” can leave the deal saying “send” after it was sent

**Where**

- `context/features/01-salesrep/wave-3-task-proposal-final.md:471-476` — finishing and sending in one command must end with the send's follow-up as the owner's next step.
- `components/pipeline/FinishTaskDialog.tsx:51-52,83-90,222-236` — the manager may untick the follow-up checkbox, sending `followUp: false`.
- `lib/commands/tasks.ts:240-260,294-307` — the server accepts `followUp: false`.
- `lib/domain/taskMutations.ts:370-396` — `markTaskDone` first unlocks the frozen step and makes it due today.
- `lib/domain/offerMutations.ts:188-205` — `recordOffer` replaces that step with a call only when `followUp` is true.

**Concrete failure scenario**

1. Jana asks for a price. The frozen step is `SEND_QUOTE`.
2. Michal chooses “Poslal som to sám”, enters the price, and unticks “Jana potom zavolá, či prišlo”.
3. The task becomes DONE and the `OFFER_SENT` row correctly says the price was sent.
4. Because `followUp` is false, the next step remains `SEND_QUOTE`, now due today. Jana is told to send a price that the system has just recorded as already sent.

**Why it matters**

This produces a directly false actionable state and can lead to a duplicate email. It also contradicts the real workflow (“after sending, plan the follow-up call”) and the approved §6.5 transaction.

**Suggested fix**

For `finishAndSendAs`, either require a follow-up and remove the opt-out, or require an explicit replacement/cleared next step when follow-up is declined. The simplest design-consistent fix is to make the follow-up mandatory in this combined command and always install its call step. Add a regression test for the current `followUp: false` payload; it must no longer leave `SEND_QUOTE`/`SEND_DESIGN` active after a successful send.

### 3. IMPORTANT — reopening can create an active deal owned by a deactivated or ineligible user

**Where**

- `context/features/01-salesrep/wave-3-task-proposal-final.md:540-543` — deactivation/role change is blocked only for open deals; closed deals intentionally keep their owner.
- `lib/commands/admin.ts:52-68,84-105,119-149` — `heldDealWork` counts only `ACTIVE`/`SNOOZED`, so deactivation or removal of `deals.receive` is allowed when the user owns only closed deals.
- `lib/commands/pipeline.ts:120-134` — reopen does not lock or validate the retained owner.
- `lib/domain/dealMutations.ts:332-360` — reopen changes status to ACTIVE but leaves `ownerId` unchanged.
- `prisma/backfill/check-concurrency.ts:384-386` — the test covers only an active, eligible retained owner.

**Concrete failure scenario**

1. Jana owns several LOST deals but no open deals. Admin deactivates Jana, or changes her role to one without `deals.receive`; Wave 3 correctly permits this because her deals are closed.
2. Michal later reopens one of those deals.
3. It becomes ACTIVE with a CALL due today, but `ownerId` still points to Jana. Jana cannot work it. It is not counted as unassigned because `ownerId` is non-null, and inactive users are absent from the normal owner/team views.

**Why it matters**

The reopening operation turns valid historical ownership into invalid live ownership and can silently strand work. This is a direct interaction between the new D14 lifecycle rule and the existing “owner kept on reopen” behavior.

**Suggested fix**

Make reopen validate the retained owner under the normal User-before-Lead lock order. If the owner is inactive or lacks `deals.receive`, require the manager to choose a valid owner in the reopen dialog, or atomically assign the acting manager / set the deal unassigned according to an explicit product decision. If ownership changes, write the normal `OWNER_CHANGED` and `DealOwnership` records in the same transaction. Add tests for both a deactivated owner and a role-demoted owner.

### 4. IMPORTANT — the official feature specification and the shipped workflow disagree

**Where**

- `context/features/01-salesrep/wave-3-task-proposal-final.md:19-26,138-145` — the approved real workflow includes price and design together, D3 says the rep chooses the task follow-up, and D4 says one task may contain both PRICE and DESIGN.
- `context/features/01-salesrep/round2-deal-workspace.md:563-578` — declares the task proposal official and says price + design together is one task; line 566 also still says it is “not implemented”.
- `components/pipeline/AskManagerDialog.tsx:19-22,42-47,83-96,153-185` — ships a single-choice radio UI and derives the step automatically.
- `lib/domain/tasks.ts:25-34` — labels combined content as Wave 4, although the backend and schema already accept arrays.
- `context/app-workflow.md:10-12,196-213`, `context/domain/operations.md:50`, and `context/progress-tracker.md:557-599,628-632` — record the later one-choice/automatic-step decision and explicitly acknowledge that the official feature file was not updated.

**Concrete failure scenario**

The real case “please give me a price and make a design” cannot be entered as one task in the shipped UI. The SR must ask for one item, wait for that task to close, then create another. At the same time, a future AI reading the official feature file will reasonably implement multi-select and a step picker, while an AI reading `app-workflow.md` will preserve single-select and automatic derivation.

**Why it matters**

This is not merely stale wording: it changes a named real workflow and the task/step state machine. The review rules say implementation is checked against the approved feature specification, while the repository currently presents two mutually exclusive sources of truth.

**Suggested fix**

Confirm which later product decision is authoritative, then synchronize the official feature proposal, its round-2 summary, app workflow, operations documentation, backlog marker, comments, and tests in one pass. If one-choice-until-Wave-4 is the intended decision, update D3/D4 and the scenarios in the official proposal instead of leaving a progress-log override. If D4 remains the requirement, change the ask UI to multi-select and add the combined-task/combined-result/overlap tests already specified in §9.

### 5. MINOR — offer overlap input can say “keep open” while cancelling the task

**Where**

- `lib/commands/offers.ts:25-44,54-58` — validation only requires `cancelTask` when `overlap === "CANCEL_TASK"`; it does not reject `cancelTask` with `KEEP_OPEN`, and it does not require a non-empty cancellation reason.
- `lib/commands/offers.ts:96-108` — any supplied `cancelTask` is executed, so it overrides the declared `KEEP_OPEN` choice; an empty reason silently becomes “už to netreba”.
- `lib/commands/dealWork.ts:145-153,198-205` — the comparable phone/follow-up command is stricter: fact-only `KEEP_OPEN` cannot carry `cancelTask`, and a non-closing cancellation requires a reason.

**Concrete failure scenario**

A stale or manipulated offer action sends `{ overlap: "KEEP_OPEN", cancelTask: { taskId, reason: "" } }`. The server returns success, records the send, and cancels the task with a generated reason even though the submitted choice says the task stays open.

**Why it matters**

The current UI does not create this payload, but server actions must validate their own semantic combinations. Otherwise a client bug produces an audit trail and task state that contradict the submitted choice.

**Suggested fix**

Add cross-field validation (or explicit checks) so `CANCEL_TASK` requires exactly one matching `cancelTask` with a non-empty reason, while `KEEP_OPEN` forbids `cancelTask`. Add crafted-payload tests for both invalid combinations.

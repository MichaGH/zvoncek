# Wave 3 implementation review — R02

Date: 2026-09-19  
Scope: verification of the R01 fixes plus a fresh review of Wave 3 manager tasks, step locking, returned results, ownership transitions, concurrency, UI flows, tests, and synchronized context.  
Review type: implementation review (read-only apart from this review record). No database command was run.

## Verdict

**Changes requested.** All five R01 findings have been addressed in the current implementation. The owner-only returned-result rule is now shared by all three user paths; finish-and-send no longer accepts the follow-up opt-out; reopen repairs an ineligible retained owner in the same transaction and revision; D3/D4 record the shipped one-choice/derived-step decision; and offer cancellation now requires a matching explicit choice and reason.

The second pass found two implementation defects that should be fixed before Wave 3 is considered complete: a real race in role changes can still leave live deal/task work on an ineligible user, and the offer dialog can enter a hidden stale-overlap state from which saving always fails. Two smaller correctness/documentation issues and the deletion of the protected feature backups are also recorded below.

## Findings

### 1. IMPORTANT — a concurrent stale profile save can remove a role while the user owns open work

**Where**

- `context/features/01-salesrep/wave-3-task-proposal-final.md:377-389` — D14 is required to be race-safe by locking the User before checking work.
- `context/features/01-salesrep/wave-3-task-proposal-final.md:547-550` — removing `deals.receive` or `requests.resolve` must be refused while the user owns open deals or has assigned OPEN tasks.
- `lib/commands/admin.ts:129-143` — `updateUserProfileAs` reads `before.role` with an ordinary `findUnique` before taking the User row lock; after the `UPDATE`, line 138 skips every work check when that stale `before.role` equals the submitted role.

**Concrete failure scenario**

1. A profile-edit transaction reads a user as `SCOUT`, and its stale form also submits `SCOUT`, but pauses before the `UPDATE`.
2. Another admin operation changes that user to `SALES_REP`; a manager then assigns an ACTIVE deal to the now-eligible user. Both operations commit.
3. The first transaction resumes, updates the row back to `SCOUT`, and evaluates `before.role === data.role` as true using its old read.
4. It returns at line 138 without calling `heldDealWork`. The user is now a SCOUT but still owns the live deal. The analogous `SALES_REP → MANAGER → task assigned → stale SALES_REP save` sequence can leave an OPEN task assigned to someone without `requests.resolve`.

The `UPDATE` does eventually lock the User row, but the decision about which capabilities are being removed is based on an unlocked, potentially stale value. This is exactly the race the Wave 3 lock rule intended to close.

**Why it matters**

It can strand an active deal or manager task on a user who cannot see or resolve it, violating D14 and the database-map invariant. The small team makes the race unlikely, but it is a data-integrity failure, not merely a transient display issue.

**Suggested fix**

Make the first read of the edited User a locking read (`SELECT ... FOR UPDATE`, following the existing User-first order), and only then derive `before.role`, update the profile, and run the capability-loss checks. Alternatively, make the update return both a reliably locked old role and the new role, but do not base the decision on the pre-lock `findUnique`. Add a concurrency regression test that pauses the stale save, promotes the user and assigns work, then resumes the stale save; the save must either detect staleness or refuse because of the newly assigned deal/task.

### 2. IMPORTANT — changing offer contents can hide the selected cancellation and make the dialog unsaveable

**Where**

- `components/pipeline/OfferSentDialog.tsx:98,108-118` — `overlap` is persistent component state, while `overlapping` is recomputed from the currently selected contents; `cancelling` depends on the stale state and the existence of a task, not on `overlapping`.
- `components/pipeline/OfferSentDialog.tsx:157-174,194-218` — the payload sends `cancelTask` whenever `cancelling` is true, but sends `overlap` only while the current contents still overlap.
- `components/pipeline/OfferSentDialog.tsx:395-420` — the only radio controls that can change the overlap choice disappear as soon as the user unchecks the overlapping content.
- `lib/commands/offers.ts:57-60` — the corrected R01 validation properly rejects `cancelTask` without `overlap: CANCEL_TASK`.

**Concrete failure scenario**

1. A PRICE task is open. In “Čo sme poslali”, the owner includes price and chooses “Už to netreba — zrušiť úlohu”.
2. Before saving, she unchecks price and leaves only “o nás” or cenník selected.
3. `overlapping` becomes false and the overlap controls disappear, but `overlap` remains `CANCEL_TASK`, so `cancelling` remains true.
4. The client submits `cancelTask` but omits `overlap`. The server correctly returns “Neplatné údaje.” every time. There is no visible control with which to clear the hidden selection; the user must close and reopen the whole dialog.

**Why it matters**

This is a normal click path in a central mobile dialog. The server prevents corrupt state, but the UI leaves the user in an unexplained, apparently permanent save failure and discards the work when they reopen.

**Suggested fix**

Derive cancellation as `overlapping && overlap === "CANCEL_TASK"`, and clear `overlap`/`cancelReason` whenever the selected contents stop overlapping the task. Apply the same state-reset principle to the phone-price overlap controls in `InteractionSheet.tsx:162,179,582-610`, where unchecking “Povedal/a som cenu” can also leave a hidden overlap choice. Add a component/state regression test for selecting cancellation and then removing the overlapping content.

### 3. MINOR — the list's “consecutive no-answer” calculation still has nondeterministic latest-event ordering

**Where**

- `context/features/01-salesrep/wave-3-task-proposal-final.md:391-394` — every rule that means “last” or “latest” must order by `(createdAt, id)`.
- `lib/queries/pipeline/index.ts:257-270` — `noAnswerStreaks` assigns `row_number()` using only `ORDER BY a."createdAt" DESC`.
- `lib/queries/pipeline/index.ts:607-611,648-651` — detail history does use `(createdAt, id)`, so the list and detail can disagree on the same events.

**Concrete failure scenario**

Two serialized contact writes can still have the same millisecond `createdAt` because PostgreSQL `now()` is the transaction start time. If one is `NO_ANSWER` and the other is a positive call/reply, the detail deterministically treats the higher id as latest, while the SQL window may choose either order. The list can therefore show “2. pokus” while the detail's latest contact is successful, or hide a real current no-answer streak.

**Why it matters**

It does not alter stored data, but it violates the explicit ordering invariant and can give the caller a wrong attempt count. This is rare but straightforward to make deterministic.

**Suggested fix**

Change the window to `ORDER BY a."createdAt" DESC, a.id DESC` and add a tie case to the ordering test.

### 4. MINOR — the R01 documentation synchronization is incomplete

**Where**

- `context/features/01-salesrep/wave-3-task-proposal-final.md:242-245` still says the ask stores a “chosen” step, although D3 and §6.1 now say PRICE/DESIGN derive it.
- `context/features/01-salesrep/wave-3-task-proposal-final.md:350` still says finish-and-send fingerprints contain a follow-up “choice”, although the R01 decision removed that choice.
- `context/features/01-salesrep/wave-3-task-proposal-final.md:359` says reopen fingerprints contain “the step chosen”, while reopen has one fixed `CALL`-today step and the file itself lists the lack of a picker as an accepted limit.
- `context/features/01-salesrep/wave-3-task-proposal-final.md:535-550` does not record the R01 rule that reopening a deal with an inactive/ineligible retained owner transfers it to the reopening manager (or nobody if the actor cannot own deals). The current rule exists only in `context/app-workflow.md:164-167`, `context/domain/operations.md:49`, and the progress log.

**Concrete failure scenario**

A later agent uses the official feature proposal's lock/fingerprint table to extend the task dialog and reintroduces an optional step or follow-up choice, or implements another reopen entry point that retains an invalid owner because the behavior is absent from the feature's reopen flow.

**Why it matters**

The primary D3/D4 contradiction is fixed, so this is not a current runtime defect. It is residual ambiguity in the official design document that already caused one implementation/spec drift in R01.

**Suggested fix**

Replace “chosen” with “derived/stored”, remove “follow-up choice” from the finish-and-send fingerprint description, describe reopen's fixed step accurately, and add the invalid-owner transition to §6.11/§6.12. Keep the historical decision notes, but make the active rules internally consistent.

# Wave 4 specification review — R01

Date: 2026-09-19  
Scope: `context/features/01-salesrep/wave-4-proposal.md` Parts A–D, checked against the shipped Wave 3 task implementation, the authoritative context files, the current test schema, and Michal's latest Wave 5 direction.  
Review type: specification review. Read-only apart from this review record. No database command, schema command, application-code change, commit, push, or deploy was performed.

## Verdict

**Changes requested.** The central architecture is good and does **not** need to be replaced: one open task per deal, the server-side step lock, independently resolved child parts, immutable delivered snapshots, and a derived combined label are the right foundation. There is no reason to add a combinatorial `SEND_PRICE_AND_DESIGN` enum or to turn tasks into the future developer-project system.

The draft is not ready to implement as written. Findings 2–3 are blockers because they leave returned-item identity and terminal state ambiguous. Findings 1 and 4–10 are concrete separation, workflow, authorship, security, or rollout gaps. Finding 11 is a required baseline gate, and finding 12 is documentation cleanup that should happen when the proposal is revised.

The most important product correction is a strict separation of two independent processes:

1. A manager HELP task records what the manager still owes the SR. In Wave 4 it may contain **Cena**, **Návrh**, and the deliberately retained manual **Iné** part.
2. The locked send step records what the client still has to receive. After Wave 5 that may contain any subset of cenová ponuka, exact cena, cenník, about-us email, návrh, and later approved client-facing contents.

Delivering a task part changes the manager-request state but does **not** remove that content from the send step. Recording that the SR actually sent a content changes the send-step state but does not resolve unrelated manager work. The two projections meet only through explicit links such as an `OFFER_SENT` fulfilling a delivered PRICE or DESIGN result.

## Findings

### 1. IMPORTANT — the proposal must make task parts and Wave 5 client-delivery contents explicitly independent

**What's wrong**

Keeping `OTHER` as a manual manager-help part is an accepted product choice. The problem is narrower: the compatibility text still risks making the future client-request selection and the manager task look like one shared vocabulary. They are not.

Wave 5 may record that the client asked for exact price, cenová ponuka, cenník, about-us email, and návrh. The resulting locked send step may contain all of those client-facing contents. A manager task, however, contains only the work for which help is actually requested: normally PRICE and/or DESIGN, with OTHER available only when the SR deliberately writes a separate internal question. Cenník and about-us email never become manager task parts merely because the client asked for them.

The proposal also derives the combined locked-step label primarily from task-part state. That works for Wave 4's current PRICE/DESIGN case, but is not the final source of truth once the same step must retain unsent contents that have no task part. The proposal should state that this is a temporary Wave 4 projection or, preferably, define an abstraction that Wave 5 can replace without changing task semantics.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:28,49-51,61-74,118-122,178-183,227-238,255-265`
- `context/features/01-salesrep/wave-4-proposal.md:229-238` describes the future choices only informally and does not define separate persisted identities for client-request contents, unsent delivery obligations, and task parts.
- `prisma/schema.prisma:393-407` and `lib/domain/tasks.ts:9-14` correctly retain today's Wave 3 `OTHER`; keeping it is not itself a defect.

**Concrete failure scenario**

The client asks for exact price + návrh + cenník. The SR deliberately asks the manager only for PRICE + DESIGN. The manager returns PRICE first. Correct behavior is:

- the task now shows PRICE done and DESIGN still waiting;
- the locked send step still says that exact price + návrh + cenník remain to be sent;
- if the SR sends exact price + cenník now, only those two client-delivery obligations disappear and the locked step becomes návrh;
- the task remains open because DESIGN is still requested.

If Wave 4 instead treats task kinds as the complete locked-step contents, cenník is lost. If it removes PRICE from the step when the manager returns it, the app falsely claims that the client already received the price.

**Why it matters**

This boundary determines whether partial sending is trustworthy. Conflating the two states either creates unnecessary manager work or removes unsent client material from the next step.

**Suggested fix**

Revise the proposal with an explicit invariant and naming boundary:

- `DealTaskPart.kind = PRICE | DESIGN | OTHER` means **work requested from the manager**. `OTHER` stays manual; no Wave 5 client choice maps to it automatically.
- Wave 5's client-request vocabulary and send-content vocabulary are separate from `DealTaskPart.kind`. A client request may suggest task checkboxes, but it never creates a task automatically.
- Manager delivery changes only the part from REQUESTED to DELIVERED. It does not mark anything sent and does not subtract it from the locked send step.
- `OFFER_SENT` (or the equivalent explicit sent action) remains the only truth that client-facing content was sent. A partial send subtracts only its recorded contents from the locked send step. Correction of that send adds the content back.
- During an OPEN task, the step remains locked against arbitrary replanning, but it is still actionable for partial fulfilment. The SR can send any currently ready subset without closing the task or planning the follow-up call.
- Use different wording/icons for **manager prepared** and **sent to client**. In the task, PRICE may be green as “pripravené” while the locked send step still lists it as unsent. Contents still waiting on the manager remain visible but disabled in the send dialog with a clear “čaká sa na manažéra” label.
- State whether Wave 4's PRICE/DESIGN-derived combined label is temporary. Before implementing it, design enough of Wave 5 to choose the durable representation of a multi-content send obligation. If Wave 5 will replace the single `NextActionKind` with persisted content rows/set data, build that small foundation first; otherwise Wave 4 may proceed behind a pure projection API that Wave 5 can replace.

### 2. BLOCKER — the proposed returned-item identity cannot represent two declined parts

**What's wrong**

The draft says the returned-item address remains `(taskId, kind, designId)` while two separately declined parts become two separately acknowledgeable items. In today's item model, however, both would have `kind = DECLINED`, no `designId`, and therefore the same key. Adding an unnamed `part` property only to prose does not fix the strict schemas, key function, fulfilment/dismissal metadata, or server validation.

The product intentionally does **not** need repeated PRICE or DESIGN lifecycles inside the same task. If a delivered price later becomes obsolete while DESIGN is still open, the team will handle the exceptional rescoping by direct conversation, a task message, or manager takeover rather than forcing another PRICE occurrence through Zvonček. `@@unique([taskId, kind])` and refusing to re-add a delivered/declined kind are therefore accepted limits, not bugs. Re-adding the same withdrawn row before it was ever delivered remains compatible with that decision.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:145,152-154,162-167,211-220`
- `lib/domain/tasks.ts:91-97` — today's `itemKey` distinguishes only task, item kind, and optional design ID.
- `lib/domain/tasks.ts:101-119` — current strict fulfil/dismiss schemas have no part identifier or declined-part kind.
- `context/domain/database-map.md:127,138-145` — current persisted metadata has the same shape.

**Concrete failure scenario**

The manager declines both PRICE and DESIGN with different reasons. The SR should acknowledge two rows. Both become `taskId:DECLINED:` under the current identity. A dismissal of one either consumes both in a set/map projection or cannot identify which reason was acknowledged.

**Why it matters**

This is not only UI wording. It affects dismissal, idempotency fingerprints, and which exact decline the SR has acknowledged.

**Suggested fix**

Use the immutable `DealTaskPart.id` as the identity of every part-originated item, or minimally add a validated `partKind` to every declined-item reference:

- Prefer `partId` in `fulfils` / dismissals because the child row already has a stable ID; keep `designId` where a particular návrh snapshot must also be identified.
- A declined result must include its exact `partId`, so PRICE, DESIGN, and OTHER declines never collide.
- Keep the accepted one-row-per-kind rule. State explicitly that DELIVERED/DECLINED parts cannot be requested again inside the same task; exceptional rescoping is handled outside this lifecycle.
- Define the exact strict metadata schemas and item-key function in the proposal before implementation.

### 3. BLOCKER — terminal `DealTask.status` has two contradictory meanings

**What's wrong**

Section 2.4 defines aggregate terminal status: if any part was delivered the task becomes DONE; otherwise a decline makes it DECLINED; otherwise it is CANCELLED. Sections 2.5 and 2.7 instead preserve today's action-based meaning: owner/system cancellation produces CANCELLED and takeover cancels a HELP task, even when a delivered part survives. The draft explicitly says returned items can exist on a CANCELLED task, which cannot happen under the §2.4 aggregate formula when any part was delivered.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:152-157`
- `context/features/01-salesrep/wave-4-proposal.md:179-184`
- `context/features/01-salesrep/wave-4-proposal.md:211-216`
- Today's action-based semantics are in `lib/domain/taskMutations.ts:201-227,523-549` and `context/domain/database-map.md:164-170,187-189`.

**Concrete failure scenario**

PRICE is DELIVERED, DESIGN is still REQUESTED. The SR cancels the task because the client no longer wants a návrh. The remaining DESIGN part becomes WITHDRAWN. Under §2.4 the task must be DONE because a price exists; under §2.5 it must be CANCELLED because the owner cancelled it. The task-history badge, `TASK_DONE` vs. `TASK_CANCELLED` secondary activity, close reason, and tests all depend on which rule wins.

The same contradiction occurs when a manager takes over, the owner is removed, the deal closes, or the manager declines the last outstanding part after an earlier part was delivered.

**Why it matters**

Two reasonable implementations will persist different statuses and history for the same business event. Status drives the inbox/lock and is also presented to people; it cannot be left as an interpretation detail.

**Suggested fix**

Add an explicit terminal transition table. The clearest continuation of Wave 3 is:

- part rows are the complete truth about what was delivered/declined/withdrawn;
- task status records **how the task ended**: normal resolver completion → DONE, manager rejection of the remaining work → DECLINED, owner/system withdrawal/takeover/owner removal → CANCELLED;
- delivered items survive independently of that status.

If aggregate status is preferred instead, remove every statement that cancellation after a partial result produces CANCELLED and make the task card rely on part rows, not the aggregate badge, to explain what happened. Whichever rule is chosen must cover mixed deliver+decline in one command, decline after an earlier delivery, owner cancellation, deal close, transfer to manager, transfer to nobody, direct takeover, and HANDOVER (which remains partless).

### 4. IMPORTANT — partial sending needs a durable delivery-obligation projection, including correction/revival

**What's wrong**

The desired rule is now clear but is not fully expressed by the proposal's task-only “in play” projection:

- manager delivery changes readiness/result state, not client-delivery state;
- only an explicit sent fact removes client-facing content from the locked send step;
- a partial send removes exactly the contents actually sent and leaves the rest locked;
- correcting/crossing out that sent fact restores the contents that are no longer supported by another active send fact.

Today's fact-only send path intentionally does not change the stored step while a task is OPEN. That is safe only while the label can be completely derived from task results. After Wave 5, a locked step can also contain cenník, about-us email, cenová ponuka, or other contents that have no task part. Task rows alone therefore cannot reconstruct “what remains to send”, and the current single `nextActionKind` cannot represent an arbitrary remaining subset.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:70-77,121-122,186-200,211-224,227-238,264-265`
- `lib/commands/offers.ts:99-137` — an offer sent while a task remains open is `factOnly` and does not update the step.
- `lib/domain/offerMutations.ts:211-229` — correcting an offer explicitly recomputes offer summaries but not the step.
- `lib/domain/tasks.ts:201-223` and `lib/domain/taskMutations.ts:112-123` — current I10 logic assumes pending returned items and the stored step stay compatible.

**Concrete failure scenario**

The client asked for exact price + návrh + cenník. The task contains PRICE + DESIGN. The manager delivers PRICE. The task correctly becomes “PRICE done; DESIGN waiting”, but the send step must still contain all three contents. The SR sends exact price + cenník; the task remains open for DESIGN and the send step must now show only návrh. If the command merely records a fact and leaves the stored single kind untouched, the UI continues to claim price/cenník are pending or loses the remaining návrh, depending on which state a screen reads.

Separately, the SR records price as sent and later corrects that activity as a mistake. The price must return to the unsent set. Today's correction recomputes price/email summaries but intentionally leaves the step unchanged, so a CALL step or a reduced DESIGN-only step can remain stale.

**Why it matters**

The list label, task card, offer dialog, command validation, and eventual unlocked step can disagree. Most importantly, the CRM may tell the SR that an unsent item is finished, or keep prompting her to send something already recorded as sent.

**Suggested fix**

Define two pure projections with separate inputs:

1. `taskOutstanding(parts)` → what the manager still owes and whether the task stays OPEN.
2. `deliveryOutstanding(requestedContents, active OFFER_SENT facts, pending task-result links/dismissals)` → exactly what the client still has to receive.

The locked step's visible content set comes from the second projection, never merely from task parts. While any manager part is still REQUESTED, keep the step locked (`nextActionAt = NULL`) against arbitrary replanning, but allow the send dialog to fulfil any **ready** subset. After each partial send/dismiss/correction, recompute the visible remaining set. Do not plan the 3–7 day follow-up while manager work or unsent delivery contents remain.

The proposal must choose where Wave 5's multi-content obligation lives. Good options are a dedicated row/set model or a stable client-request record plus ledger projection; serializing an arbitrary combination into `NextActionKind` is not future-proof. Every change must run under the existing Lead lock/revision rule, and the canonical idempotency fingerprint must include the exact subset sent.

Call the projections after every relevant mutation: part delivery/decline/withdraw/add, offer fulfilment, explicit dismissal, offer correction, task cancellation/closure, takeover, owner change, and deal close/reopen. Add matrix tests for price-first/design-first, unsupervised contents such as cenník, partial sends in both orders, retry of the same subset, two-tab sends of overlapping subsets, correction before/after task closure, and cancellation/takeover after one result was consumed.

### 5. IMPORTANT — “whatever field is filled is delivered” will accidentally deliver an existing price

**What's wrong**

The proposed manager dialog uses field presence as the selection of which parts are finished. Today's dialog pre-fills the price and breakdown from the deal. On a combined task, opening the dialog to return only the návrh will therefore also submit the pre-existing price, even if the manager never intended to confirm it as this task's result.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:104-116`
- `components/pipeline/FinishTaskDialog.tsx:43-47` — the price fields are initialized from `Lead.price` / `priceNote`.
- `components/pipeline/FinishTaskDialog.tsx:73-92` — today's save submits the price whenever the task wants PRICE and the field contains a valid amount.

**Concrete failure scenario**

The deal already has an old rough price of €700. A combined PRICE + DESIGN task is open. The manager has completed only the design, opens “Hotovo”, selects the návrh, and submits. Because €700 was pre-filled, “whatever is filled” marks PRICE DELIVERED too, freezes €700 as the manager's returned price, closes the task, and tells the SR both parts are ready.

**Why it matters**

This can send an obsolete price to a client and prematurely close the task. It is especially likely because pre-filling the current price is useful and already shipped.

**Suggested fix**

Separate **selection** from **value**. Each requested part needs an explicit “Odovzdať teraz” checkbox/toggle; values may be pre-filled, but only selected parts are submitted. The button count comes from selected parts, not non-empty fields. The server accepts an explicit list of part operations and rejects data supplied for an unselected part. “Poslal som to sám” uses the same selected subset.

### 6. IMPORTANT — the notes cutover would falsely label legacy `Lead.note` data and does not choose one canonical location for new intake notes

**What's wrong**

The proposal correctly says `Lead.note` has been overwritten by contact edits and first calls, then proposes relabelling it “Poznámka pri pridaní kontaktu”. That label is not true for existing rows. The proposal also says a new scout note becomes the first `LeadNote` while `Lead.note` remains the read-only intake note, but never says whether new creation writes one field, both, or how the two are displayed without duplication.

It also does not inventory every current writer that must stop. First calls, call-stage contact edits, and deal contact edits all write the mutable field today.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:271-280,313-325`
- `lib/actions/contacts/index.ts:80-110,118-145` — contact creation and contact editing write `Lead.note`.
- `lib/commands/calls.ts:74-102` — a first-call note becomes both the CALL note and a replacement `Lead.note`.
- `lib/domain/dealMutations.ts:88-95,119-148` and `components/pipeline/DealDetail.tsx:169-181,757` — deal editing still treats it as mutable contact data.

**Concrete failure scenario**

A scout wrote “web občas nejde”. The first caller later replaced it with “majiteľ chce modrú stránku”. After Wave 4 the UI labels the surviving text “Poznámka pri pridaní kontaktu”, falsely attributing the caller's text to the scout. On a new contact, an implementer may write both `Lead.note` and a GENERAL `LeadNote`, causing the same note to appear twice; another implementer may write only `LeadNote`, leaving an old call/contact view empty if that read path was missed.

**Why it matters**

The purpose of Part B is reliable authorship. Starting it by asserting a false origin would make historical notes less trustworthy than they are now.

**Suggested fix**

Specify an exact cutover:

- Existing non-null `Lead.note` is frozen and displayed as **“Staršia poznámka (autor/pôvod neznámy)”**, not as a scout note. Do not mass-copy it into an authored `LeadNote` unless a deterministic source can be proven.
- New contact intake writes one canonical GENERAL `LeadNote` in the same transaction as the new Lead. Decide whether `Lead.note` is left null for new rows or mirrors it temporarily; do not leave this to implementation. Prefer no new writes to the legacy field once every reader is migrated.
- Remove `note` from contact/deal edit payloads and UIs, and remove the first-call overwrite. Inventory all paths above.
- A positive first-call handoff note may remain on the CALL activity for truthful contact history and also become a FOR_CALL note only if the duplicate is deliberately linked/deduplicated in the combined notes/history view. State whether it is pinned automatically.
- Add migration/cutover tests proving old text is unchanged and never falsely attributed.

### 7. IMPORTANT — note visibility and edit history are not specified strongly enough to prevent leaks or false authorship

**What's wrong**

The draft says INTERNAL is manager-only and that notes are shown in call/deal headers, but it does not define who may add/read each kind in call stage vs. deal stage, or how an INTERNAL pinned note is kept out of a telesales/SR header. “Author edits own; manager edits any” also mutates `body` while preserving the original author and role. A manager could rewrite Jana's note and the UI would still say Jana wrote that text. `deletedAt` alone cannot support the claim that deletion “stays in history”: there is no deleter, reason, original-body revision, or note audit event.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:281-315,317-328`
- Proposed schema at `context/features/01-salesrep/wave-4-proposal.md:285-302`
- Implementation outline at `context/features/01-salesrep/wave-4-proposal.md:389-391`
- Server-side scope and out-of-scope `NOT_FOUND` requirements are in `context/code-standards.md:31-37` and `context/architecture.md:65-66`.

**Concrete failure scenario**

Michal pins an INTERNAL note (“customer pays late”). The call-sheet query fetches all pinned notes as §3.2 broadly says, and the SALES_REP sees it because the proposal never requires per-kind server filtering. In another case Michal edits a FOR_CALL note written by Jana; the card still attributes the rewritten text to Jana because only `authorId/authorRole` exist.

**Why it matters**

This is a permission leak and an audit-integrity issue in a feature whose reason for existing is trustworthy origin.

**Suggested fix**

Add an explicit matrix before implementation:

- who may create each kind in CALL_STAGE and DEAL_STAGE;
- who may read it (INTERNAL must be filtered in the server query, never only hidden in the component);
- who may pin/unpin, edit, and delete after ownership/stage changes;
- which existing lead guard/scope each command and query uses, with out-of-scope `NOT_FOUND`.

Prefer append-oriented corrections: either notes are immutable and an edit creates a revision/correction record, or add `updatedById` plus an immutable audit event containing the old and new body. Soft deletion needs at least `deletedById` and an audit row/reason if it is promised as history. Every existing-Lead note mutation still needs `withLockTx`, expected revision, an idempotency key/fingerprint, and exactly one Lead revision bump.

### 8. IMPORTANT — Part C cannot copy an SR handover note during an unrelated direct takeover

**What's wrong**

Part C says that when a handover is accepted **or the manager takes over**, “the SR's handover text” becomes a pinned FOR_BUILD note authored by the SR. A direct takeover may have no HANDOVER task and therefore no SR handover text. Its optional note is written by the manager. Copying it as an SR-authored note would fabricate authorship; copying a HELP task's request would turn an unrelated price/design request into an order brief.

The accepted-handover path is also broader than one button: it can happen through direct takeover while a HANDOVER task is open, the owner selector, or bulk transfer to a resolver. All use the shared owner transition and must behave identically.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:331-336`
- `lib/commands/tasks.ts:422-480` — direct takeover receives a manager-authored optional note and a new step.
- `lib/domain/taskMutations.ts:507-549` — `ownerTransition` accepts HANDOVER or cancels HELP depending on the open task.
- `lib/domain/taskMutations.ts:512` call sites include `lib/commands/tasks.ts:475`, `lib/commands/pipeline.ts:191,348`, and `lib/domain/dealMutations.ts:380`.

**Concrete failure scenario**

There is no open task. Michal clicks “Preberám klienta” and writes “volal som s majiteľom”. The proposed rule has no SR-authored handover text to copy. If implementation copies Michal's note but sets `authorId` to the former SR, the permanent build brief is false. If it copies nothing on this button but does copy through the owner selector, equivalent handover acceptance paths disagree.

**Why it matters**

FOR_BUILD is intended to survive into the later developer project. False authorship or copying the wrong request would send production work from an unreliable brief.

**Suggested fix**

Create the automatic FOR_BUILD note **only when an actual OPEN HANDOVER task is accepted**. Copy exactly `DealTask.text`; author = `requestedBy`; creation actor/audit = the manager who accepted. Put this operation inside the shared `ownerTransition` HANDOVER branch so takeover, owner selection, and bulk transfer cannot diverge, and make it idempotent in the same transaction. A direct takeover without HANDOVER may optionally create a separate manager-authored FOR_BUILD note through an explicit field/action, but must not impersonate an SR.

## Workflow after the fixes

The intended combined path uses one locked next step, but two separate state machines:

1. In Wave 5 the SR records that the client asked for exact price + návrh + cenník. This creates/updates the client-facing delivery obligation and the locked display says “Poslať cenu + návrh + cenník”. It does not automatically create manager work.
2. The SR deliberately creates one HELP task with PRICE + DESIGN because only those two contents need the manager. The task gets two requested parts. Cenník exists only in the client-delivery state.
3. The manager explicitly selects PRICE as “deliver now”, returns the exact price, and leaves DESIGN requested. The task shows PRICE ✓ and DESIGN waiting. The locked client step is unchanged because nothing has yet been sent.
4. Common path: the SR waits. The manager later delivers DESIGN, closing the task. The SR sends price + návrh + cenník together; the sent fact fulfils both returned task parts and all three client-delivery contents. Only then does the app plan “Zavolať, či prišlo”.
5. Less common path: while DESIGN is still requested, the SR sends exact price + cenník. The PRICE `partId` is fulfilled and those two contents leave the delivery obligation. The task remains OPEN for DESIGN, the step remains locked with no date, and its visible contents reduce to “Poslať návrh”. No follow-up call is planned yet.
6. When DESIGN is delivered, the task closes but the návrh remains unsent. The now-unlocked due-today step still says “Poslať návrh”. Sending it fulfils the DESIGN result and empties the delivery obligation; the app can then plan the 3–7 day follow-up.
7. If a sent activity is corrected, only the contents no longer supported by another active sent fact return to the delivery obligation. Decline, withdrawal, cancellation, takeover, close, correction, and owner change never erase an immutable delivered manager result or an active sent fact.

`OTHER` remains valid for a deliberate internal manager question and its answer/acknowledgement flow. It is not populated from Wave 5 client-request checkboxes and does not itself become a client-facing send content.

## Accepted design choices — not findings

- `DealTaskPart` is justified; partial delivery is materially clearer as rows than as repeatedly merged JSON.
- One OPEN task and one locked next step remain appropriate for this small company. The known fixed-appointment/multiple-future-step limit does not require redesign here.
- No combinatorial `SEND_PRICE_AND_DESIGN` enum is needed. The combined display label should ultimately be derived from the client-delivery obligation; in Wave 4, deriving the currently supported PRICE/DESIGN subset through a replaceable pure projection is acceptable.
- Delivered snapshots must remain immutable and survive later changes to `Lead.price` or a `Design`.
- The future developer role/project must stay separate from manager HELP tasks.
- Existing `OFFER_SENT` remains the truth of what the client actually received; Wave 5's “asked for” data must not replace it.
- `OTHER` may remain a combinable manual HELP part. It is internal manager assistance, not a catch-all mapping for client-facing requests.
- One PRICE, one DESIGN, and one OTHER row per task is an accepted simplicity limit. Revised scope after a delivered/declined part is handled by direct discussion, a task message, manager takeover, or a later fresh task after the current one closes.

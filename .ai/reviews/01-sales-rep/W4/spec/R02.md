Date: 2026-09-20  
Scope: the rewritten `context/features/01-salesrep/wave-4-proposal.md`, checked against the shipped Wave 3 task
implementation, the shipped Wave 5 request/receipt projection, the current Prisma schema, authoritative context, and

Review type: specification review. No database command, schema command, application-code change, commit, push or
deploy was performed. This review record is the only file added by this review.

> The previous tracked W4 `R01.md` is a historical review of the superseded v1 proposal and is currently deleted in

> or overwrite it; the rewritten proposal receives the next round number, R02.

## Verdict

**Changes requested. Do not start Part A schema work yet.**

The central design is sound and should be kept: one open manager task per deal, separate task parts, Wave 5 remaining
the only source of truth for what the client still has to receive, a locked but partially actionable step, immutable
manager-result snapshots, and no combinatorial `NextActionKind` enum. The rewritten proposal also correctly keeps
manager work (`PRICE | DESIGN | OTHER`) separate from client intent (`INFO | PRICELIST | PRICE | DESIGN | REVIEW`).

Part A nevertheless has three blockers:

1. its aggregate task-status rule still conflicts with the specified cancellation activities and history;
2. its proposed `PartView` cannot represent multiple returned návrhy or distinguish sent items from dismissed items;
3. a mixed `OTHER + PRICE/DESIGN` task has no defined fallback step once the sendable work disappears while `OTHER`
   remains open.

The remaining findings are narrower but should be resolved in the specification before Claude implements them. In
particular, the current price prefill would accidentally deliver a price, correction behavior is described two
different ways, and the finish-and-send rule does not explicitly use the complete Wave 5 outstanding set.

The proposal's existing gates are valid and remain gates: Wave 5 F4 acceptance, the P0 locked-mode fix, and Michal's
answer to Q9. Parts B–D are explicitly not implementation-ready until Q5–Q8 are answered; Part A can proceed separately
after findings 1–7 below and those existing gates are resolved.

## Findings

### 1. BLOCKER — the derived terminal status still contradicts whole-task cancellation and its activities

**What's wrong**

Section 2.4 makes `DealTask.status` an order-independent aggregate of its parts: no requested part + any delivered part
means `DONE`. Q10 explicitly confirms that product decision. But the command table says all existing `cancelTask`
paths keep their meaning and write `TASK_CANCELLED`, and the edge-case section says a delivered part can survive a
task whose status is `CANCELLED`.

Those statements cannot all be true. After one part is delivered, the aggregate formula makes `CANCELLED` impossible.
The same contradiction affects `declineTaskAs`: declining all remaining work after an earlier delivery produces a
`DONE` task by Q10, but the command is specified to keep `TASK_DECLINED` as its keyed primary event.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:199-228` — aggregate status plus task-level secondary events.
- `context/features/01-salesrep/wave-4-proposal.md:370-378` — `declineTaskAs` and `cancelTask` claim their old meaning
  remains unchanged.
- `context/features/01-salesrep/wave-4-proposal.md:484-488` — says delivered parts survive a `CANCELLED` task.
- `context/features/01-salesrep/wave-4-proposal.md:813-817` — Q10 decides delivered + declined/withdrawn ends `DONE`.
- Current action-based behavior is `lib/domain/taskMutations.ts:201-227,412-437,512-549`.

**Concrete failure scenario**

The task contains PRICE + DESIGN. The manager delivers PRICE. The client then decides they no longer want the návrh,
so the owner chooses “Zrušiť úlohu” and the remaining DESIGN part becomes `WITHDRAWN`.

- The status table and Q10 require `DealTask.status = DONE`.
- The cancellation contract requires `DealTask.status = CANCELLED` and a `TASK_CANCELLED` event.
- The history may therefore say “Úloha zrušená” while the task badge says “Vybavené”, or two reasonable implementers
  may store different statuses for the same action.

The same mismatch occurs on close, takeover, removal of the owner, bulk transfer, and “decline the rest” after one
part was delivered.

**Why it matters**

`OPEN` controls the step lock and inbox, while terminal status and `TASK_*` rows are user-visible history. An ambiguous
terminal transition will produce contradictory cards and makes conversion/testing nondeterministic.

**Suggested fix**

Keep Q10 and make it normative everywhere:

- Parts are the truth about each outcome.
- The final task status is exactly the aggregate table in §2.4.
- A whole-task cancellation means “withdraw every still-requested part”, then recompute the aggregate status. It emits
  `TASK_CANCELLED` only when the resulting status is actually `CANCELLED`. If an earlier delivered part makes the
  result `DONE`, emit the part-withdrawal event and the normal task-completed event; the UI may say “Vybavené — cena
  odovzdaná, návrh zrušený”.
- Likewise, declining the remaining parts after an earlier delivery must not produce a task-level “Zamietnuté” badge
  or a primary event that claims the whole task was declined.
- Add one terminal transition table covering: normal delivery, mixed deliver+decline in one command, decline after an
  earlier delivery, owner withdrawal, close, takeover, owner removal and bulk transfer. State the exact primary and
  secondary activity types for every row.

Also remove the contradictory schema comment that `resolvedById` may be `NULL` for a system transition
(`wave-4-proposal.md:178-180`): §2.7 B8 correctly says every current path has an acting user and always fills it
(`wave-4-proposal.md:392-394`).

### 2. BLOCKER — `taskPartState` cannot represent partial consumption or dismissal of a part

**What's wrong**

A DESIGN part may return several návrhy. Each návrh is an independently addressable returned item, and each may be
sent or dismissed separately. The proposed `PartView` has only one part-level `receivedAt` and receives only two lists
of bare `ItemRef`s (`fulfils` and `dismissed`). That input contains no receipt timestamp, dismissal time, reason or
actor, so the declared `receivedAt` cannot even be computed by the pure function as typed.

More importantly, “consumed” conflates two opposite facts:

- sent to the client (`OFFER_SENT`), which may use a green client-receipt mark;
- deliberately not sent (`TASK_RESULT_DISMISSED`), which must never look like a client receipt.

The state table's single `DELIVERED + consumed = ✓ sent` rule is therefore false for a dismissed price/design and
insufficient for a DESIGN part with two returned designs.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:146-160` — part-level state table.
- `context/features/01-salesrep/wave-4-proposal.md:192-223` — item identity and dismissal/fulfilment references.
- `context/features/01-salesrep/wave-4-proposal.md:231-265` — impossible `PartView.receivedAt` contract and bare
  `consumed` input.
- `context/features/01-salesrep/wave-4-proposal.md:437-455` — card presents one mark per part.
- Current one-item-per-design behavior is `lib/domain/tasks.ts:168-201`; dismissals carry a reason in
  `lib/domain/taskMutations.ts:140-184`.

**Concrete failure scenario**

The manager returns návrhy A and B in one DESIGN part. The SR sends A and chooses “Neposielam” for B with the reason
“klient vybral A”. Both items are now consumed, but only A reached the client.

The proposed projection can only see that A is in `fulfils` and B is in `dismissed`. It has one `receivedAt` for the
whole part and no dismissal metadata. A card that reduces the part to `✓ Návrh poslaný` lies about B; a card that keeps
the part `◆ pripravené` lies that something is still waiting; and the pure signature cannot produce the displayed
date in either case.

The simpler one-price case also breaks: a dismissed PRICE part has `receivedAt = null` and no waiting item, which is
indistinguishable from malformed/missing consumption unless a third state exists.

**Why it matters**

This is the audit trail for what the manager delivered and what the client actually received. Collapsing sent and
discarded results can make the CRM assert that the client saw material they never received.

**Suggested fix**

Model consumption per returned item, not per part. For example:

```ts
type PartItemView = PendingItem &
  | { disposition: "WAITING" }
  | { disposition: "SENT"; receivedAt: string; activityId: string }
  | { disposition: "DISMISSED"; at: string; by: Person; reason: string | null; activityId: string };

type PartView = {
  // part lifecycle fields...
  items: PartItemView[];
};
```

Pass enriched fulfilment/dismissal facts (including the canonical offer instant and dismissal metadata) into the pure
projection. Derive the part's compact mark only for display: all waiting = prepared; mixed = “1 z 2 poslaný”; all
sent = sent; any dismissed = say so explicitly. Keep the item rows available in the expanded card. Add tests for two
designs: both waiting, one sent/one waiting, one sent/one dismissed, both sent in different emails, correction of one
send, and a dismissed price.

### 3. BLOCKER — mixed `OTHER + PRICE/DESIGN` tasks can be locked on a completed or nonexistent send step

**What's wrong**

`OTHER` deliberately maps to no client-facing content. The proposal permits it in any combination and lets the owner
add or withdraw parts later. P6 says re-derive a locked step from Wave 5 outstanding work, but `defaultStep` returns
`null` when no client-facing content remains. The proposal does not say what locked step replaces the send step while
an `OTHER` part is still `REQUESTED`.

There is a second form of the same hole. P6 is guarded by `isSystemStep`. An `OTHER`-only task may preserve a deliberate
CALL/WAITING/CUSTOM step. If the owner later adds PRICE or DESIGN, that old step is not a system step, so the proposed
guard prevents the new send-bearing work from becoming the locked headline.

No previous step snapshot is stored on `DealTask`, so blindly replacing the step on add also gives the system nothing
to restore if the send-bearing part is later withdrawn or sent while `OTHER` remains open.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:97-100,135-142` — `OTHER` maps to no content.
- `context/features/01-salesrep/wave-4-proposal.md:159-160` — all combinations/re-addition are allowed.
- `context/features/01-salesrep/wave-4-proposal.md:267-303` — P3/P6 and the event table.
- `context/features/01-salesrep/wave-4-proposal.md:370-375` — add/withdraw contracts.
- `context/features/01-salesrep/wave-4-proposal.md:472-480` — promised UI headline.
- `lib/domain/clientRequests.ts:283-290,310-349` — OTHER is absent from the outstanding projection and
  `defaultStep([])` returns `null`.
- `lib/domain/tasks.ts:42-56` — current `stepAfterTask` retains a chosen step for OTHER but does not persist a fallback
  outside `Lead.nextAction*`.

**Concrete failure scenarios**

1. The task is PRICE + OTHER. The manager returns PRICE; the SR sends it; OTHER is still being answered. The Wave 5
   outstanding set is now empty because OTHER maps to no content. The task is still OPEN, so the step must stay locked,
   but P6 has no derived step to store. Leaving the old value shows “Poslať cenu” after the price was sent.
2. The task starts as OTHER with a deliberate “Zavolať v piatok” fallback. The owner adds PRICE. Because CALL is not a
   system step, P3 prevents re-derivation and the locked card continues to say CALL instead of “Poslať cenu”. If the
   implementation overrides it anyway, withdrawing PRICE later cannot restore the original Friday call because it
   was never stored anywhere.

**Why it matters**

These are allowed, ordinary combinations in the proposal. They can hide newly requested manager work or keep telling
the rep to send something that is already sent, with no way to edit the step while the task is locked.

**Suggested fix**

Choose and specify one fallback model before schema work. The least surprising model is to persist the pre-task
post-completion step snapshot on the task (kind, note, mode and schedule as applicable). Then define:

- while client-facing outstanding is non-empty, the locked headline follows Wave 5 outstanding even if the earlier
  fallback was CALL/WAITING/CUSTOM;
- while only OTHER remains, the locked card says it is waiting for the manager and displays the persisted fallback as
  “Po vybavení”, without falsely presenting completed send work;
- if a send-bearing part is added, withdrawn, sent or revived, switching between the outstanding-derived step and the
  fallback is deterministic;
- closing the task restores/unlocks that fallback unless remaining client-facing outstanding requires a send step.

If no fallback is to be persisted, then combining OTHER with send-bearing parts or adding them across that boundary
must be forbidden. That is a worse UX and contradicts the accepted “Iné is combinable” decision, so persisting the
fallback is preferable. Add full transition tests for OTHER→add PRICE, PRICE+OTHER→send PRICE, withdrawal back to
OTHER-only, and correction of the price send.

### 4. IMPORTANT — field presence will accidentally deliver a prefilled existing price

**What's wrong**

The proposal says “whatever is filled in is delivered” and uses one dialog with no explicit per-part selection. The
current dialog deliberately pre-fills PRICE from `Lead.price` and `Lead.priceNote`. Therefore a manager opening a
combined task to return only a návrh will also return the pre-existing price, even if that price is old and the manager
did not touch it.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:459-471`.
- `components/pipeline/FinishTaskDialog.tsx:43-47,126-153` — amount and breakdown are prefilled from the deal.
- `components/pipeline/FinishTaskDialog.tsx:73-83` — current payload includes the price whenever the task wants PRICE.

**Concrete failure scenario**

The deal contains an old rough €700 price. A PRICE + DESIGN task is open. The manager has completed only the návrh,
opens “Hotovo”, selects Variant A and submits. €700 was already filled, so the proposed rule marks PRICE delivered,
freezes €700 as the immutable task result, and may close the whole task.

**Why it matters**

The rep is told a stale price came back from the manager and may send it to the client. This is particularly likely,
not an exotic malformed-client case.

**Suggested fix**

Separate selection from values. Every requested part needs an explicit “Odovzdať teraz” toggle. Values may remain
prefilled, but only selected parts are submitted. The server input must contain an explicit list of operations and
reject values supplied for an unselected part. The button count and “what remains open” copy use the selected parts,
not field non-emptiness. Use the same selected subset in “Poslal som to klientovi sám”.

### 5. IMPORTANT — correction behavior is specified both as “never touch the step” and “re-derive while locked”

**What's wrong**

P6 says whenever outstanding changes while a task is open, the locked step follows it. The event table and B2 then
make corrections an explicit exception: crossing out a send never changes step fields. Later, the edge-case section
says the same correction re-derives the locked step. These are mutually exclusive command contracts.

This cannot be dismissed as wording: the user cannot repair the stored next step by hand while it is locked.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:281-303` — P6 and event table.
- `context/features/01-salesrep/wave-4-proposal.md:327-332` — B2 says correction never touches the step.
- `context/features/01-salesrep/wave-4-proposal.md:497-498` — edge case says correction re-derives it.
- Current shipped rule is `lib/domain/offerMutations.ts:267-287` and `context/app-workflow.md:213-215`: corrections
  reconcile facts but never edit `Lead.nextAction*`.

**Concrete failure scenario**

PRICE was sent while a task remains open for OTHER. The command reduced the locked send step. The SR later crosses out
that PRICE send as a mistake. PRICE becomes outstanding again, but the stored locked kind may still be SEND_EMAIL/CALL
or another narrower value. Under B2 it stays stale and the SR cannot edit it; under §2.10 it is changed automatically.

**Why it matters**

Claude cannot implement both rules, and the resulting list label, note, and post-task unlock behavior differ.

**Suggested fix**

Make one rule normative and delete the other statement. The safer Wave 4-specific rule is:

- corrections still never replan an **unlocked** user step (Wave 5 remains unchanged);
- while a task is OPEN, correction may call the same explicit command-owned `refreshLockedStep` as partial sends,
  because the user cannot repair a locked step manually;
- it changes only the app-owned locked kind/note, keeps date `NULL`, mode `SCHEDULED`, status unchanged, and writes the
  same planning audit convention as P6.

If Michal prefers the old “never touch it” rule even while locked, state that the warning/headline is the intended
repair and add a test for every stored kind. In either case, make §2.6, §2.10 and `w4StepLocked` agree.

### 6. IMPORTANT — “nothing else pending” must mean the complete Wave 5 outstanding set, not only task items

**What's wrong**

The `finishAndSendAs` contract says a follow-up call is planned only when the task closes and nothing else is pending,
but it does not name the canonical check. The current implementation's `otherPending` check looks only at returned
task items. Wave 5 added client requests (INFO, PRICELIST, REVIEW, PRICE, DESIGN), so task-item emptiness is no longer
enough.

The proposal's test matrix also tests older returned items but does not explicitly cover unsent client requests that
have no task part.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:372,404-433`.
- `context/features/01-salesrep/wave-4-proposal.md:553-567` — no finish-and-send case with unrelated open requests.
- `lib/commands/tasks.ts:298-320` — current command checks only other pending task items.
- `lib/domain/offerMutations.ts:239-260` — `followUp: true` checks I10 task items, not all `LeadRequest` work.
- Canonical work definition: `context/app-workflow.md:228-244` and
  `lib/domain/clientRequests.ts:251-303`.

**Concrete failure scenario**

The client asked for INFO + PRICELIST + PRICE + DESIGN. The manager finishes PRICE + DESIGN and chooses “Poslal som to
klientovi sám”, sending only those two. The task closes and there are no other returned task items, but INFO and
PRICELIST remain open. An implementation copied from today's `otherPending` logic schedules “Zavolať, či prišlo” and
replaces the system send step even though two promised contents were never sent.

**Why it matters**

The follow-up call can hide unfinished client work — exactly the class of drift Wave 5 was created to remove.

**Suggested fix**

State the server invariant explicitly: after recording the offer and reconciling requests, a CALL follow-up is allowed
only when the task will be closed **and** `outstandingOf(tx, lead.id)` is empty. Otherwise the command derives the
remaining send step; while any requested part remains, it stays locked. This must be server-enforced, not inferred
from the dialog. Add cases where INFO/PRICELIST/REVIEW remain, where they are included in the same email, and where an
older delivered task item remains.

### 7. IMPORTANT — the S-13a backfill has a multi-day write gap before the code cutover

**What's wrong**

The implementation order adds and backfills `DealTaskPart` before any Part A code, then spends several steps/days
implementing domain, reads and commands while the current app continues writing only `DealTask.contents/result`.
Any task created, completed, declined or cancelled after the first backfill has missing or stale part rows when reads
switch to the new table.

The conversion is described as repeatable, but the implementation order never requires a final catch-up conversion
under a no-write window immediately before the read switch/drop.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:717-770` — staged schema and one conversion.
- `context/features/01-salesrep/wave-4-proposal.md:860-878` — schema/backfill occurs before several implementation
  steps, with no final catch-up gate.
- Current writes use only the parent fields: `lib/domain/taskMutations.ts:243-437`.

**Concrete failure scenario**

S-13a converts all existing tasks on Monday. On Tuesday, while Claude is implementing the new readers, Michal creates
a PRICE task and the manager completes it through the still-running current UI. The parent row has `contents` and
`result`, but no `DealTaskPart`. On cutover, the new reader sees no delivered part; after S-13b the only structured
result is dropped.

**Why it matters**

This can lose test evidence and make the new implementation appear correct on seeded fixtures while real test tasks
vanish. The same pattern would be dangerous in any future environment that already contains tasks.

**Suggested fix**

Define an explicit cutover:

1. S-13a adds the table; initial conversion may populate fixtures.
2. Until all readers/writers are ready, either dual-write parts from the old commands or treat the environment as
   task-read-only.
3. Immediately before switching reads, stop task writes, rerun the idempotent conversion in one transaction, and
   verify **every** HELP task has the exact expected parts/results and no part disagrees with the parent.
4. Switch code, run the full suite and human checks, then perform S-13b only after a second zero-drift verification.

Production currently has no task tables, so the final production DDL remains additive; say explicitly that the test
conversion is never run on production and production receives the final parent+parts schema directly.

### 8. IMPORTANT — the Notes permission/edit contract can leak INTERNAL notes and misattribute manager edits

**What's wrong**

Part B says “INTERNAL notes only for managers” without defining whether that restricts creation, reading, or both.
It also permits a manager to edit anyone's note, but the model stores only the original `authorId/authorRole` and an
`updatedAt`. A manager can therefore rewrite a scout's sentence and the UI will still attribute the resulting content
to the scout.

Soft deletion likewise stores only `deletedAt`; “stays in history” has no deleting actor, reason, or immutable prior
body unless an activity/audit contract is added.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:587-615` — proposed model.
- `context/features/01-salesrep/wave-4-proposal.md:617-632` — display and proposed permissions.
- The deal-detail query currently gives a rep every BUSINESS row in scope (`lib/queries/pipeline/index.ts:669-693`),
  illustrating why future note visibility must be filtered server-side rather than hidden in a component.

**Concrete failure scenarios**

1. A manager creates an INTERNAL note containing pricing strategy. If “manager-only” was interpreted as creation-only,
   the owner SR receives it in the same notes query and sees it in the detail or pinned action-sheet header.
2. A scout writes “majiteľ chce modrú stránku”. A manager edits the body to “klient nepotvrdil rozpočet”. The card
   still says the scout authored the new statement. There is no way to establish what the scout actually wrote.

**Why it matters**

The first is a permission leak. The second corrupts authorship — the main reason Part B introduces `LeadNote` instead
of continuing to overwrite `Lead.note`.

**Suggested fix**

Resolve Q5 with a normative server policy:

- INTERNAL means manager-only to create **and read**; every list/count/detail/header query applies the visibility
  predicate before returning notes. UI hiding is not permission.
- Prefer immutable bodies: authors may add a correction/new note; managers may pin/unpin and soft-delete with a
  reason. If editing is required, add `updatedById` plus append-only edit history (old body, actor, time), and render
  “upravil X”.
- Add `deletedById` and optional deletion reason or an audit activity; define whether deleted content remains visible
  to managers only.
- Test SR/telesales/scout/manager access directly, including pinned headers, counts and a role change after writing.

This finding does not block Part A, but Part B must not start from the current seven-line Q5 sketch.

### 9. IMPORTANT — existing `Lead.note` rows cannot truthfully be labelled “note when contact was added”

**What's wrong**

The proposal correctly documents that `Lead.note` has been overwritten by first calls and later contact edits, then
proposes displaying every surviving value as read-only “Poznámka pri pridaní kontaktu”. That attribution is knowingly
false for existing rows. It also does not choose a canonical write for new contacts: the scout's input becomes the
first `LeadNote`, while `Lead.note` supposedly remains the intake note, but the spec does not say whether creation
writes one field or both and how duplicate display is prevented.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:575-585` — confirms the field is overwritten today.
- `context/features/01-salesrep/wave-4-proposal.md:621-632` — labels it as the original intake note and also creates a
  first `LeadNote`.
- Current writers: `lib/actions/contacts/index.ts:80-145`, `lib/commands/calls.ts:74-102`, and
  `lib/domain/dealMutations.ts:150-166`.

**Concrete failure scenario**

A scout entered “web občas nejde”. The first caller later overwrote it with “majiteľ chce modrú stránku”, and a later
contact edit may have changed it again. After Part B the UI labels the surviving text as the scout's intake note. For
a newly added contact, another implementation may write the same text to both `Lead.note` and a pinned GENERAL
`LeadNote`, displaying it twice.

**Why it matters**

The new notes feature would confidently invent provenance for old data while still leaving two possible canonical
locations for new data.

**Suggested fix**

Define a cutover rule:

- Existing non-empty `Lead.note` is shown as **“Staršia poznámka (autor/pôvod neznámy)”**, not as an intake note.
- From the cutover onward, new scout input is written once, canonically, as a GENERAL `LeadNote` in the same contact
  creation transaction. Stop all later writers from mutating `Lead.note`.
- Either leave `Lead.note` frozen only for legacy display, or backfill it into notes with `authorId = null` and an
  explicit legacy origin (which would require the schema to allow unknown authors). Do not duplicate a new note in
  both places.
- Inventory and test every existing writer before making the field read-only.

This also does not block Part A, but it blocks Part B.

### 10. MINOR — the destructive conversion fallback must be an explicit user decision, not an automatic plan step

**What's wrong**

Section 6.3 says that any ambiguous conversion falls back to wiping and reseeding the test database. Endpoint guards
prevent touching production, but they do not make deletion of the current test data harmless. The test database now
contains Wave 3/Wave 5 click-through state that may be useful for verifying this exact migration.

**Where**

- `context/features/01-salesrep/wave-4-proposal.md:757-770`.
- `context/ai-workflow-rules.md:23-37` and `context/code-standards.md:90-92` require reviewed, guarded, repeatable
  backfills that abort on ambiguity.

**Concrete failure scenario**

The dry run finds one malformed historical task. The implementation follows the proposal literally and wipes the test
database instead of reporting that row. The feature data needed to reproduce the ambiguity is gone, even though a
targeted repair or explicit user-approved reset may have been preferable.

**Why it matters**

This is recoverable test data, not production data, so it is not a rollout blocker. It is still a destructive choice
that should not be automatic.

**Suggested fix**

Change the fallback to: abort and report the exact rows; make no write. Wipe/reseed only after Michal explicitly chooses
that option for the verified test endpoint. Keep the triple endpoint guard and confirmation flag.

## Confirmed strengths / not findings

- **The task and the client request are separate processes.** Cenník, info and rozbor never become task parts. `OTHER`
  remains a deliberate internal manager question. This is correct.
- **No combined next-step enum is needed.** The stored kind remains categorical and the Wave 5 projection derives the
  combined headline. This is the right future-proof boundary.
- **One open task per deal is still appropriate.** Parts solve the real parallel manager-work case without turning the
  CRM into a general project manager.
- **A delivered result is not a receipt.** Only a valid `OFFER_SENT` means the client received it. The proposal states
  this correctly.
- **The accepted limit on planning a separate future call while a manager task is open is a product decision, not a
  bug.** This review does not ask for multiple next steps.
- **One assignee for all parts is acceptable for this wave.** The future developer project remains a separate feature;
  Wave 4 should not pre-build it.
- **P0 is real and correctly identified by the proposal.** Current `lib/domain/clientRequests.ts:341-348` still ignores
  `opts.locked` when choosing the changed-kind mode. It remains a prerequisite, not a new review finding.
- **Q9's proposed separation is correct:** declining manager work must not silently withdraw what the client asked
  for. It still needs Michal's explicit confirmation because §9 lists it as a gate.

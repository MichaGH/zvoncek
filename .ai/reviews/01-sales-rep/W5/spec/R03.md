# Wave 5 specification review — R03

Date: 2026-09-20  
Scope: `context/features/01-salesrep/wave-5-proposal.md` draft v3 and `R02-response.md`, checked against the current
Wave 3 / 3a implementation, authoritative context, the Wave 4 integration boundary, and the production-conversion
contract.  
Review type: final specification review. Read-only apart from this review record. No database command, schema command,
application-code change, commit, push, or deploy was performed.

## Verdict

**One blocker and four localized corrections remain. Do not implement the draft exactly as written yet.**

This is no longer an architectural problem. The request ledger, chronological reconciliation, migration identity,
full next-step transition, grouped request projection, close/reopen policy, permissions, and Wave 4 boundary are now
sound. The R02 blockers were genuinely addressed rather than papered over.

The remaining blocker is a missing input to the canonical projection: a Wave 3 manager result remains actionable after
its task is closed, but `clientRequestState(requests, receipts, openTask)` can see only the open task. That would drop
the existing “manager returned a price/návrh; SR has not sent it yet” state whenever no `LeadRequest` independently
keeps the same content open.

Findings 2–5 are smaller contradictions/clarifications. They do not require a redesign or a new database concept.
After these are incorporated, the proposal is suitable to freeze and implement on the test branch, subject to the
already documented Wave 3 human click-through gate.

## What is now ready

The following parts passed this review and should not be reopened without new evidence:

- `LeadRequest` as an event ledger rather than a lifetime array.
- `INTERESTED` as the one new first-call outcome; requested contents remain separate rows.
- Exact-price snapshots in `OFFER_SENT`; phone and email both count as received.
- One deterministic reconciliation using request instants and `offerInstant`, including backdated sends, corrections
  and same-call phone-price links.
- The explicit migration origin, unique migration key, provenance and nullable historical actor.
- The complete five-field next-step defaults and the decision not to store combinatorial next-action enums.
- Explicitly submitted next steps winning inside their command, without background mutation of `Lead.nextAction*`.
- Raw request events for history/statistics versus grouped contents for actionable work.
- Open requests becoming dormant on close and driving the default step again on reopen.
- Manager editing rights and server-side scope.
- Wave 5 owning client intent/receipt while Wave 3/4 tasks own manager work.

## Findings

### 1. BLOCKER — the canonical projection omits returned task results after the task closes

**What's wrong**

The proposal correctly says that the checklist contains three sources of client-facing work:

1. open client requests;
2. work currently being made in an OPEN manager task;
3. a PRICE or DESIGN result the manager already returned but the SR has not sent or dismissed yet.

The proposed canonical function accepts only `requests`, `receipts` and `openTask`. In the shipped Wave 3 model, the
third source does **not** belong to the open task. Finishing a task changes it to DONE; its immutable result is then
projected by `pendingItems()` until an `OFFER_SENT.meta.fulfils` or `TASK_RESULT_DISMISSED` consumes it. The detail query
loads those pending items separately from `openTask` for exactly that reason.

This is not always masked by a client request. Wave 3 allows a rep to ask the manager for PRICE, DESIGN or OTHER
manually. A returned PRICE/DESIGN can therefore be waiting even when no `LeadRequest` of that content exists. The
current I10 invariant still requires the step to remain “Poslať cenu/návrh”.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:149-151` — checklist explicitly includes pending returned results.
- `context/features/01-salesrep/wave-5-proposal.md:301,305` — `sendCompletesStep` and task transitions must include them.
- `context/features/01-salesrep/wave-5-proposal.md:407-419` — canonical projection signature includes only
  `(requests, receipts, openTask)`.
- `context/features/01-salesrep/wave-5-proposal.md:438-442` — Wave 3 returned items are promised as projection input.
- `lib/domain/tasks.ts:165-199` — returned/pending items come from closed DONE/DECLINED tasks, not the open task.
- `lib/domain/tasks.ts:201-223` — pending PRICE/DESIGN constrains the step and send completion.
- `lib/queries/pipeline/index.ts:643-648,713-717` — detail query loads `pending` independently from `openTask`.

**Concrete failure scenario**

The client has no Wave 5 request row because the rep manually asked the manager for a price after discussing the case
internally. The manager finishes the task with €1,200. The task is now DONE, so `openTask = null`; no `LeadRequest(PRICE,
OPEN)` exists. `clientRequestState(requests, receipts, openTask)` returns no outstanding content. The returned price
disappears from the combined checklist, `sendCompletesStep` may offer a follow-up call, and the SR can miss sending the
manager's result even though Wave 3 currently prevents that.

The same failure occurs after a DESIGN task is DONE, and it remains possible when a client request was withdrawn while
the manager result still awaits the owner's explicit “send” or “Neposielam” decision.

**Why it matters**

This would regress a shipped Wave 3 data-integrity invariant and create exactly the forgotten-work case Wave 5 is meant
to eliminate. It also gives Wave 4 no stable API for its delivered task parts.

**Suggested fix**

Make the canonical projection consume all relevant task state, not only the open task. For example:

```text
clientRequestState(requests, receipts, {
  openTask,
  pendingItems
})
```

or pass one existing canonical task projection that exposes both “being made” and “returned, not yet consumed”. Then:

- open PRICE/DESIGN task content contributes `robí sa`;
- pending PRICE/DESIGN contributes `pripravené`, even if no client request exists and the task is DONE;
- `OTHER`/DECLINED remain internal acknowledgement items and never become send contents;
- grouped outstanding content is the union of request obligations, open task sendable work and pending sendable items;
- the same union drives headline, checklist, warning, step default, send pre-ticks and `sendCompletesStep`;
- Wave 4 later swaps the Wave 3 task projection for `taskPartState` without changing the client-request API.

Add a test with **no LeadRequest**: finish a PRICE task → task DONE → price remains prepared/outstanding → send consumes
it. Repeat for DESIGN and for correction of the consuming send.

### 2. IMPORTANT — “covered by the current step” and the visible headline are undefined when a manual step differs from the dominant request

**What's wrong**

The draft now preserves an explicitly submitted step, which is correct. It also says the visible headline always names
all outstanding contents, and that the list warning appears only when an open request is not covered by the current
step. It never defines coverage when those two facts disagree.

No persisted manual/automatic flag is necessarily required: a lower-priority stored kind that differs from the
dominant outstanding kind already proves the user selected a different immediate plan. But the read projection needs a
normative rule or the list, detail, pills and warning can describe different work.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:88-92` — warning depends on whether the current step covers a request.
- `context/features/01-salesrep/wave-5-proposal.md:139-165` — visible headline is said to list every outstanding row.
- `context/features/01-salesrep/wave-5-proposal.md:308-317` — an explicit stored step wins and survives reconciliation.
- `context/features/01-salesrep/wave-5-proposal.md:391-400` — full-step table does not define the read-time coverage rule.
- `context/features/01-salesrep/wave-5-proposal.md:471` — Q7 relies on that undefined rule.

**Concrete failure scenario**

PRICE and DESIGN are open. The normal default is SEND_DESIGN with a combined visible headline “Poslať návrh + cenu”.
The rep explicitly chooses SEND_QUOTE because she promised to send the price now and the návrh later. Correctly, the
stored kind remains SEND_QUOTE.

Possible implementations from the current prose are contradictory:

- show “Poslať návrh + cenu”, hiding that the immediate explicit plan is price first;
- show “Poslať cenu” with no DESIGN warning, hiding the unsent návrh;
- show “Poslať cenu” plus “⚠ Chceli návrh”, which accurately represents both facts.

**Why it matters**

This is the principal edge case that motivated partial fulfilment. A misleading headline can make the preserved manual
step effectively invisible even though the database kept it correctly.

**Suggested fix**

Define one pure `coveredContents(stepKind, outstanding)` rule and use it everywhere. A simple policy consistent with
the current priority is:

- request-default/task-locked dominant step: combined headline contains the whole grouped outstanding union;
- a stored SEND kind below the dominant outstanding kind is an explicit narrower plan: headline shows the stored step,
  and uncovered contents appear in the warning/checklist;
- CALL / WAITING_FOR_CLIENT / CUSTOM cover no send content, so every outstanding content remains a warning;
- when no content is outstanding, headline falls back to the stored step as already decided;
- document what SEND_EMAIL, SEND_QUOTE and SEND_DESIGN cover (including INFO / PRICELIST / REVIEW) so TypeScript and
  list SQL/counts cannot invent different mappings.

Add the exact PRICE-first-while-DESIGN-remains scenario to the tests, including list row, detail headline and pills.

### 3. IMPORTANT — the close/reopen test asserts the opposite of the normative rule

**What's wrong**

Section 6.10 and the R02 response deliberately changed reopen behavior: outstanding content supplies the send step,
and fixed “Zavolať” is used only when nothing remains. Test 17 still says reopening shows the fixed “Zavolať” step.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:421-430` — normative reopen rule.
- `context/features/01-salesrep/wave-5-proposal.md:500` — opposite test expectation.
- `context/features/01-salesrep/wave-5-proposal.md:589` — R02 resolution repeats the normative rule.

**Concrete failure scenario**

A closed deal still has an OPEN DESIGN request. The implementation correctly reopens it on SEND_DESIGN today. A test
written literally from §10.17 fails and pressures the implementation agent to restore CALL, contradicting the design.

**Why it matters**

Tests are the executable contract. Leaving the opposite expected result in the test list makes a correct implementation
look wrong.

**Suggested fix**

Replace test 17 with two explicit cases:

1. outstanding DESIGN/PRICE exists → reopen uses the §6.8 dominant send step, due today;
2. nothing is outstanding → reopen uses fixed CALL today with `REOPEN_STEP_NOTE`.

### 4. IMPORTANT — “crossing out a call keeps asks” is not an existing operation and conflicts with the first-call revert contract

**What's wrong**

The tests require “crossing out a call does not silently remove asks”, but the shipped app has no generic call
cross-out operation. Correctable business records are OFFER_SENT, SMS_SENT and CLIENT_REPLIED. The only call reversal is
the first-call `revertCallResultAs`, and Wave 5 explicitly says that operation deletes the request rows sourced by that
call when it is still safe to revert.

The test therefore either cannot be written or accidentally authorizes a new follow-up-call correction feature that
the proposal never designs.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:303-304` — send correction versus first-call revert have different
  defined behavior.
- `context/features/01-salesrep/wave-5-proposal.md:482-483` — contradictory/impossible call-cross-out test.
- `lib/domain/offerMutations.ts:209` — current correctable types exclude CALL.
- `lib/commands/history.ts:32-140` — the existing call reversal is specifically the call-queue first-call revert.

**Concrete failure scenario**

An implementation agent tries to satisfy §10.5 by adding CALL to the generic correctable types. A rep can now cross out
a follow-up call, but the specification says nothing about its next step, request source rows, phone PRICE receipt,
task overlap, revision semantics or statistics. That is unrequested scope and creates new inconsistent states.

**Why it matters**

The false test can introduce a feature and mutation path outside Wave 5 instead of protecting existing behavior.

**Suggested fix**

Remove “crossing out a call does not silently remove asks” from test 5. Keep the two real contracts:

- correcting an OFFER_SENT reconciles requests without changing unrelated call history;
- reverting the latest first call deletes that call's unsatisfied request rows and is refused once any is satisfied.

If generic follow-up-call correction is wanted later, design it as a separate feature.

### 5. MINOR — the pencil operation does not state which request states may be withdrawn

**What's wrong**

`setClientAsksAs` accepts request row IDs to withdraw, but the proposal does not say whether only OPEN rows are legal.
Allowing a SENT row to become WITHDRAWN retroactively destroys the meaning of its valid `resolvedActivityId`; refusing
it is the natural interpretation of “už nechcú návrh”, but the command contract should say so.

The audit payload is also named only as `added` / `removed`. With repeated same-content request events, content names
alone cannot identify which row was withdrawn.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:94-96,242-248,280-281`
- `context/features/01-salesrep/wave-5-proposal.md:288-292,302`
- `context/features/01-salesrep/wave-5-proposal.md:377`

**Concrete failure scenario**

Two PRICE requests exist; the first is SENT and the second is OPEN. The client withdraws the second. An implementation
that selects by content may withdraw the SENT row or both. History can no longer explain which occurrence was pending
and which receipt satisfied the earlier one.

**Why it matters**

It is a small contract gap, but the whole reason for row IDs is to keep repeated request events unambiguous.

**Suggested fix**

State that manual withdrawal accepts only same-lead `OPEN` row IDs; SENT and already WITHDRAWN rows return STALE. One
withdrawal may target all currently open rows of a grouped content when the user means “už to nechcú”. The audit row
stores exact request IDs plus contents; its fingerprint uses the sorted submitted row IDs, added contents and reason.
Clarify that the reason is mandatory when `withdraw[]` is non-empty (and whether add-only correction needs one).

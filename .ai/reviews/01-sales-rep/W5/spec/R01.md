# Wave 5 specification review — R01

Date: 2026-09-20  
Scope: `context/features/01-salesrep/wave-5-proposal.md`, checked against the current Wave 3 / 3a implementation,
the authoritative context files, the current test schema, the pending old-send conversion, and Michal's clarified
production meanings.  
Review type: specification review. Read-only apart from this review record. No database command, schema command,
application-code change, commit, push, or deploy was performed.

## Verdict

**Changes requested. Do not implement from the current draft yet.** The central product direction is sound:

- what the client asked for must be separate from what the client actually received;
- cenník and an exact calculated price must remain separate;
- the current price and the last price the client received must remain separate;
- manager work is separate again from both of those facts;
- an arbitrary combination should be shown as a derived checklist, not encoded in combinatorial `NextActionKind`
  values.

The draft nevertheless has five implementation blockers. Most importantly, it currently treats “the client knows
this” as identical to “we no longer have to send this”, although a price told by phone is deliberately still followed
by a written price email. It also compares a lifetime category set against a lifetime send ledger, which cannot tell a
new request from an old request already fulfilled months ago. The exact ask-to-send mapping is incomplete, the current
first-call idempotency can silently lose one of several selected wishes, and the promised integration with today's
single-content Wave 3 task can produce the wrong stored headline.

The production direction should **not** reuse the old `quoteSentAt` or `priceDisclosed` columns as the new model. The
safe meaning of “use the same field for exact price” is: keep the canonical `PRICE` content and convert each confirmed
old exact-price disclosure into an `OFFER_SENT` PRICE snapshot. `ClientAsk.PRICE` means that the client requested a
price; it is not the migration destination for evidence that a price was sent.

Wave 3 is already implemented on the test branch; only its human click-through remains. This review therefore assumes
the documented order: finish that Wave 3 gate → finalize and implement Wave 5 → re-review and implement Wave 4. Wave 5
must work with the existing one-content task during that interval.

## Michal's feedback and reviewer corrections — 2026-09-20 (read before the findings)

This section records Michal's response after reading R01 and corrects places where the reviewer misunderstood the
intended product. It supersedes the affected wording in the original findings below; the findings remain as the audit
record that prompted the discussion.

### R01-1 — resolved product rule: PRICE is seen through either phone or email

Michal clarified that the important distinction is simply:

- somebody filled/changed the current price on the lead; versus
- the client actually saw/heard that exact price, whether by **phone or email**.

Therefore any valid PRICE receipt with its exact amount snapshot—EMAIL or PHONE—means the client saw that price and may
satisfy the PRICE checklist row. A written confirmation email is not a second mandatory PRICE obligation in Wave 5. If
the SR wants to email-confirm a phone price, she may still explicitly keep/choose `SEND_QUOTE`, but the price card must
not claim that the client has never seen the amount. Under this clarified rule, original finding R01-1 is resolved as a
product misunderstanding rather than a blocker.

### R01-2 — repeated PRICE does not justify a request-occurrence system by itself

Michal restated the important distinction:

- anybody may fill or change the **current price** on the lead;
- separately, the CRM must know the exact price the client actually saw/heard, by phone or email.

That second fact already has the right representation: every recorded PRICE send/phone disclosure snapshots the
amount in `OFFER_SENT`; `Lead.price` remains the editable current amount. The UI compares the latest sent price snapshot
with the current price:

```text
Current Lead.price = €1,200
Latest valid sent PRICE snapshot = €900
→ client saw €900; current €1,200 has not been sent

Record PRICE €1,200 by email or phone
→ a new sent snapshot is created; client now saw €1,200
```

The user performs no extra maintenance beyond the existing actions: fill/change the lead price, and when the client
actually receives it, record PRICE in “Čo sme poslali” or “Povedal/a som cenu”. A same-amount resend still creates a new
dated send row and completes the current `SEND_QUOTE` action.

Because asked-vs-got is a useful summary rather than the central workflow engine, a full per-occurrence request ledger
may be unnecessary complexity. A simpler accepted contract is available:

- `Chceli` = deal-level summary of contents the client has asked for;
- `Klient dostal` = dated receipt history, including exact price snapshots;
- `Ďalší krok` = what must happen now, including a repeated request for a category already received;
- a repeated PRICE request sets `SEND_QUOTE` again; recording the new PRICE send completes that current step and updates
  the last-seen snapshot;
- the existing price mismatch warning handles the important recalculation case.

If this simple contract is chosen, R01-2 is downgraded from a blocker to a documented limitation: the `Chceli` summary
does not count separate occurrences of the same request. A rare repeated same-content request is current work because
the call sets the next step again, not because another PRICE value is appended to the summary. The final specification
must state this explicitly and test same-amount and changed-amount resends.

### R01-3 / R01-13 — reviewer recommendation: remove `NOTHING_SPECIFIC`

Michal questioned whether telesales can consistently distinguish “Info / ukážky” from “Nič konkrétne – len email”,
and whether the extra concept is worth its implementation cost. The reviewer agrees that it is probably not.

“Nič konkrétne” describes the client's attitude, not a deliverable. Statements such as “pošlite niečo”, “pošlite
informácie” and “dobre, pošlite email” cannot be divided reliably between the two choices by different callers. The
recommended four client-request contents are therefore:

```text
Info / ukážky
Cenník
Konkrétna cena
Návrh
```

Selection guidance: when the client merely says “pošlite niečo”, telesales selects **Info / ukážky**. The SR may still
send extra cenník/review material proactively; it appears only under “Klient dostal”. If the company later wants to
measure a polite brush-off versus real interest, that should be a separate call-quality/coaching signal, not a fake
email content.

Removing `NOTHING_SPECIFIC` eliminates its exclusivity rule and its unsatisfied checklist row. The remaining mapping is
direct, apart from the separately decided channel rule for PRICE: INFO → ABOUT_US, PRICELIST → PRICELIST, PRICE → PRICE,
DESIGN → DESIGN; REVIEW remains sent-only and is never a client ask.

### R01-4 — confirmed as an implementation integration fix, not a product redesign

Michal correctly understood this finding as a consequence of applying Wave 5 to current code. The existing first-call
retry identity compares only the one coarse outcome. Once the call carries multiple asks, the implementation must add
the canonical selected ask set to the idempotency fingerprint. This does not add a user-visible concept and does not
make the workflow more complicated.

### R01-5 — reviewer correction: the visible headline must list every outstanding content

The reviewer incorrectly presented “Poslať návrh” as the headline a user should see for PRICE + DESIGN. Michal's
intended UX is:

```text
Visible headline: Poslať návrh + cenu
  ○ Návrh
  ○ Cena

After price is sent:
Visible headline: Poslať návrh
  ○ Návrh
  ✓ Cena
```

There is still no combinatorial database enum such as `SEND_DESIGN_AND_PRICE`, `SEND_PRICE_AND_PRICELIST`, etc. The
separation must be explicit:

- `Lead.nextActionKind` is one internal broad category used for filtering, scheduling and ordering (for example
  `SEND_DESIGN` when návrh is among the remaining contents);
- the **human-visible headline** is derived from every outstanding checklist row and says “Poslať návrh + cenu +
  cenník” as applicable;
- after a partial send, the derived visible headline immediately removes only the sent subset;
- when nothing remains, the send flow offers/plans the follow-up call.

The current Wave 5 draft is ambiguous because §3.7's example visibly says only “Poslať návrh” while §7 promises a
combined display label. The final specification must correct the example and consistently distinguish the internal
classification from the combined visible headline.

Wave 4 is still required for the manager task itself to select PRICE + DESIGN together. Michal accepts the implementation
order Wave 5 → Wave 4 and states that both must be finished before production rollout. Therefore the one-content task
gap may be treated as a temporary test-branch limitation between waves, provided Wave 5 exposes the final projection
that Wave 4 consumes and nothing is deployed in that intermediate state.

### R01-6 — proposed production assumption can remove the permanent legacy-ask mode

Michal proposed an explicit migration rule for old production records: **for existing data, treat every confirmed
content the client received as content they asked for**. If approved as the business truth, the production-clone
backfill can populate the new ask summary after canonical receipt conversion:

| Confirmed old/canonical received content | Backfilled `Chceli` |
|---|---|
| ABOUT_US | INFO / ukážky |
| PRICELIST | Cenník |
| PRICE with a verified snapshot | Konkrétna cena |
| DESIGN | Návrh |
| REVIEW | nothing — proactive material |

Open unfinished deals need one additional rule so pending work is not lost: a current `SEND_QUOTE`, `SEND_DESIGN` or
`SEND_EMAIL` step whose matching receipt is absent adds PRICE, DESIGN or INFO respectively. Old rows with neither
confirmed receipt nor an active send step remain empty. This can remove the need for a permanent special legacy mode,
but it must be rehearsed and verified on the production duplicate before approval.

### R01-7 — production schema/code alone cannot prove the old data's real meaning

The reviewer does **not** know with certainty that every old “Cenová ponuka” row contains a recoverable exact-price
snapshot. The repository schema proves only that production could hold:

- mutable current `Lead.price` / `priceNote`;
- `quoteSentAt` (CP marked sent);
- `priceDisclosed` (client knows a price);
- old send activities.

It does not prove that the current amount still equals the amount sent at the old date, that every flag combination is
consistent, or that an undo did not leave contradictory evidence. Michal's operational memory is important business
input, but the actual live combinations have not been measured in this review.

A Prisma schema from the Git commit deployed to production is necessary but **not sufficient**. The safe evidence set
is:

1. the exact Git commit/version currently deployed, including its Prisma schema and the old commands/UI that wrote the
   fields;
2. a fresh Neon branch/duplicate of the live production database;
3. a read-only actual-schema dump/introspection from that duplicate;
4. a read-only inventory of every relevant field/activity combination and exceptions.

Michal does not need to hand-write a description from memory. In a separately authorized migration-planning session,
the team can create the duplicate and generate an inventory report there—never on live production. At minimum it must
count and classify `quoteSentAt`, `priceDisclosed`, current price present/missing, about-us evidence, old send
activities/undo patterns, designs, and the explicit cenník recipients.

The earlier decision to remove `quoteSentAt`, `aboutUsSentAt` and `priceDisclosed` means: first translate their confirmed
meaning to canonical send rows and verify it; only then remove those obsolete weaker copies in a separately approved
non-additive cleanup. It does **not** remove `Lead.price`, `priceNote`, canonical receipt history, designs or tracking.
Keeping the old columns temporarily after the first compatible deployment is a valid safer staging choice; they must be
ignored as live truth and removed only after reconciliation is accepted.

### R01-8 — clarification of the CALL example

The “PRICE warning remains” means a separate checklist warning, not that two `nextActionKind` values are stored:

```text
Next step: Call Monday
Outstanding checklist: exact price not sent
```

With the app's one-next-step model, manually selecting CALL replaces the stored SEND action. The checklist is the
passive safety net that keeps the unsent material visible. The earlier correction example was intentionally stressing
this edge but was phrased confusingly.

Recommended rule: a deliberate manual CALL / WAIT / CUSTOM step wins and is never silently overwritten by a later
send correction. Correcting the mistaken design send reopens DESIGN in the derived checklist/warning, while the manual
CALL remains. If the team never schedules a call before sending the promised material, this path will be rare. Tracking
both a send and a fixed appointment as two scheduled actions remains the already accepted separate limitation.

### R01-9 — confirmed: undo of the positive first call must undo the selected asks

Michal confirmed the expected behavior. If telesales selected PRICE + DESIGN on the wrong contact and immediately
reverts the call, the revert must restore the contact to its pre-call state: no pipeline entry, owner/handoff, send step,
or Wave 5 ask selections. Contact data and scout-origin information remain. The reverted activity remains only as audit
history. Existing first-call-note behavior is a separate notes concern and does not weaken this requirement.

### R01-11 — redesign the positive outcome boundary instead of making WANTS values imitate contents

Michal objected that mapping PRICE + DESIGN to only `WANTS_DESIGN` is not future-proof. The reviewer agrees with the
domain concern. `CallOutcome` and client asks are different dimensions:

- outcome = what happened in the contact (`NO_ANSWER`, `BAD_NUMBER`, positive interest, etc.);
- asks = zero/one/several concrete contents the client requested;
- next step = what we plan to do in the future.

The clean design is **not** to turn `CallOutcome` itself into an array. Keep one mutually exclusive call outcome, but
stop writing a content-specific `WANTS_*` value for new multi-select positive first calls. A candidate compatible shape
is:

```text
Activity.outcome = POSITIVE
Activity.meta.asked = [PRICE, DESIGN]
Lead.askedFor = [PRICE, DESIGN]      // current/deal summary if retained
visible next action = Poslať návrh + cenu
internal nextActionKind = broad scheduling/filter classification only
```

The existing `WANTS_QUOTE`, `WANTS_DESIGN` and `WANTS_EMAIL` enum values and historical rows remain readable; removing
them would be destructive and unnecessary. New handoff logic keys off a valid positive outcome plus a non-empty
validated ask set. History labels render the concrete asks (“Majú záujem: návrh + cena”), and future demand statistics
read the asks rather than the coarse outcome.

This separation means adding another client-request content later does not require inventing a matching
`CallOutcome.WANTS_*` or pretending that outcome and next step are mirrors. The final Wave 5 specification must decide
whether to reuse today's existing `POSITIVE` value for first calls or add a clearer additive positive-interest value,
then inventory every current code path that assumes `isHandoffOutcome(WANTS_*)`.

## Findings

### 1. BLOCKER — “client received PRICE” is not the same as “the price email is finished”

**What's wrong**

The proposal uses valid `OFFER_SENT` rows both for the “Klient dostal” knowledge line and for subtracting rows from the
remaining-to-send checklist. That is not true for PRICE. Today a price told by phone is intentionally recorded as
`OFFER_SENT(channel: PHONE, contents: [PRICE])`, but the next step remains “Poslať cenu” because the amount should
normally be confirmed by email. Under the proposed comparison, that phone record checks PRICE off and may make the
last checklist row complete.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:91-98,136-149,176-183`
- `context/features/01-salesrep/round2-deal-workspace.md:880-890` — the shipped rule explicitly says a phone price is
  normally followed by `SEND_QUOTE` for written confirmation.
- `lib/commands/dealWork.ts:237-255` — a phone price writes a real `OFFER_SENT` containing PRICE.
- `lib/domain/tasks.ts:212-222` — today's send-completion rule treats a PRICE content as completing `SEND_QUOTE`.

**Concrete failure scenario**

1. The client asks only for an exact price.
2. On the next call the SR says €1,285 and ticks “Povedal/a som cenu”.
3. The CRM correctly records that the client knows €1,285 and keeps “Poslať cenu” so it can be confirmed in writing.
4. Wave 5 sees a valid PRICE send, checks the only requested row, and says that nothing remains. Depending on the
   implementation, the screen either shows an all-green checklist beside `SEND_QUOTE`, or it advances to the follow-up
   call and silently drops the written confirmation.

**Why it matters**

This is a normal shipped workflow, not a theoretical edge case. One projection cannot represent both client knowledge
and the promised email obligation unless channel semantics are defined.

**Suggested fix**

Define two named projections:

1. `clientKnowledge`: any valid PRICE fact, by EMAIL or PHONE, means the client has heard/seen that price.
2. `deliveryOutstanding`: define which channels satisfy each requested deliverable. If the existing rule is retained,
   a requested PRICE is removed from the email checklist only by an EMAIL PRICE send; PHONE PRICE updates knowledge but
   not the written-send obligation.

If Michal instead wants a phone price to finish the request, record that as an explicit product-rule change and remove
the current automatic email-confirmation behavior. Do not let the implementation choose implicitly.

### 2. BLOCKER — a lifetime `askedFor[]` set compared with lifetime sends cannot represent a later request

**What's wrong**

`Lead.askedFor` is proposed as the current unique category list, while receipt is derived from every valid send in the
deal's history. There is no occurrence identity or time boundary connecting a request to a later send. Adding PRICE to
a set that already contains PRICE does nothing; any old PRICE row immediately makes it look fulfilled. The same issue
exists for a new návrh after an earlier design was sent and for resending material that the client did not receive.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:25-34,80-84,107-111,126-155,189-196`
- `lib/domain/offers.ts:100-140` — knowledge is deliberately a lifetime summary of valid send rows.
- `lib/domain/offers.ts:160-170` — each content currently collapses to yes/no/unknown, without a request occurrence.

**Concrete failure scenario**

The client received €900 in June. In September the scope changes and the client asks for a new exact price. PRICE is
already in `askedFor`, and the June `OFFER_SENT` already satisfies PRICE. The new call writes no distinguishable current
obligation, no warning appears, “Požiadať manažéra” does not preselect price, and the SR can forget the new quote.

Likewise, a client who received návrh A can later ask for a new proposal or a meaningful redesign. A generic DESIGN
ask is immediately considered fulfilled by the old design send.

**Why it matters**

The stated purpose of Wave 5 is to ensure that a literal client request cannot be missed. The proposed data shape fails
exactly when a category is requested again.

**Suggested fix**

Persist enough request identity to answer “was this content sent after the latest still-active request?” An additive
append-only request event/row is safer than trying to infer it from one array. One possible model is a small
client-request ledger carrying lead, content, requested time/activity, and withdrawal/replacement evidence, with
`Lead.askedFor` retained only as an optional read summary. The UI still has no statuses to maintain; the server derives
them.

At minimum, define per-content `lastRequestedAt`/request identity and the satisfaction rule. PRICE also needs a decision
on whether the matching sent snapshot must represent the current recalculated amount. DESIGN needs a decision on
whether any design satisfies the new ask or whether the ask/result is tied to a particular new design cycle. If the
business deliberately accepts “each category can be requested only once per deal”, state that as a known limitation;
it is not future-proof behavior.

### 3. BLOCKER — the exact ask → receipt / delivery mapping is missing, and `NOTHING_SPECIFIC` cannot currently finish

**What's wrong**

The proposal defines five ask values but five different offer contents after REVIEW is added. They are not one shared
vocabulary. INFO presumably maps to ABOUT_US, PRICELIST/PRICE/DESIGN map by name, REVIEW is sent-only, and
NOTHING_SPECIFIC has no corresponding send content at all. Nevertheless §3.7 says every “Chceli” row becomes checked
from `OFFER_SENT`, and the last checked row finishes the step.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:38-47,57-68,100-105,136-149,176-192`
- `lib/domain/offers.ts:12-21` — today's canonical sent vocabulary.

**Concrete failure scenario**

The telesales person selects only “Nič konkrétne – len email”. The SR sends an ordinary first email containing Info and
Rozbor webu. An implementation may:

- leave NOTHING_SPECIFIC forever outstanding because no offer content has that name;
- treat ABOUT_US as satisfying it;
- treat any EMAIL send as satisfying it, including an email containing only a návrh;
- remove it immediately because it is not a real content.

All four outcomes are compatible with the current text, and they produce different steps and statistics.

**Why it matters**

This controls warnings, pre-ticks, send completion, and whether a follow-up is planned. It cannot remain an implementation
guess.

**Suggested fix**

Add a normative matrix for every ask:

- the sent content(s) that satisfy it;
- eligible channel(s), including the phone-price decision from finding 1;
- whether a specific design/result identity is required;
- the visible checklist label;
- the coarse compatibility outcome and default headline.

State explicitly that REVIEW is never an ask and never becomes manager work. If NOTHING_SPECIFIC is kept, the likely
rule is that it is a statistical intent label satisfied by the approved basic first-email contents, but the exact
contents must be chosen. Normalize the selected array server-side: unique, canonical order, at least one, and
NOTHING_SPECIFIC mutually exclusive. Never trust a client-supplied coarse outcome that disagrees with the ticks.

### 4. BLOCKER — first-call idempotent replay can silently lose one of the selected wishes

**What's wrong**

The current first-call idempotency identity contains only actor, lead, source, and the single coarse outcome. Wave 5
maps several ask combinations to the same outcome (for example, every combination containing DESIGN maps to
`WANTS_DESIGN`). Reusing the same idempotency key after the selection changes will therefore replay the first success
instead of reporting a conflict or saving the new payload.

The deal follow-up path already has a full canonical fingerprint, but the proposal does not say to add the ask delta to
it.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:54-68,109-111,182-192,228-233`
- `lib/commands/calls.ts:23-32,42-48,79-89` — no ask input or full payload fingerprint is stored.
- `lib/domain/idempotency.ts:12-39` — `idempotentReplay` compares only the coarse outcome and basic identity.
- `lib/commands/dealWork.ts:156-184` — the follow-up path has a canonical `fp`, which Wave 5 must extend with the exact
  ask addition/removal.

**Concrete failure scenario**

A mobile submit with `[DESIGN]` times out after committing. Before retrying, the UI still lets the user add PRICE but
reuses the same key. Both payloads derive `WANTS_DESIGN`. The server returns the earlier success and PRICE is never
stored, although the screen appears saved.

**Why it matters**

It silently violates the feature's core promise. A normal retry becomes data loss.

**Suggested fix**

Give the first-call row a canonical full fingerprint in `Activity.meta.fp` and compare it on every replay, including
the sorted exact asks, note, callback data, schedule, and email. Preserve the current replayed recipient response for a
handoff. Add the sorted ask delta/current list to the existing `logFollowUpAs` fingerprint. Test same key + same asks,
same key + changed asks, reordered asks, a parallel double submit, and a lost race after the Lead lock.

### 5. BLOCKER — today's single-content manager task can overwrite the combined headline with the wrong step

**What's wrong**

The proposal promises to work before Wave 4, using the existing Wave 3 one-content task. However, today's
`stepAfterTask` derives the stored locked step only from the task content and older returned items. It knows nothing
about the Wave 5 client-request set. Asking the manager for PRICE therefore changes the headline to `SEND_QUOTE` even
when an unsent DESIGN request should dominate it. Closing the task merely unlocks that same stored kind.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:13-17,113-159,203-219`
- `lib/domain/tasks.ts:25-53` — PRICE task → `SEND_QUOTE`, DESIGN task → `SEND_DESIGN`.
- `lib/domain/taskMutations.ts:55-58,243-275` — task creation persists the supplied derived kind; finishing only makes
  that kind due today.

**Concrete failure scenario**

The client asks for DESIGN + PRICE. Until Wave 4, the SR can ask for only one manager content, so she first asks for the
price. The new checklist correctly contains DESIGN and PRICE, but the current task operation changes the locked headline
to “Poslať cenu”. The deal lands under the wrong step pill/label, and when the task finishes it unlocks as “Poslať cenu”
although DESIGN remains the dominant unsent item.

**Why it matters**

This is the exact transitional architecture the proposal says it supports. The checklist and the stored step would
disagree immediately.

**Suggested fix**

Wave 5 must change the task-step integration contract now: task creation/finish/cancel should ask the Wave 5 projection
for the correct stored headline from client delivery obligations + pending returned items + current task readiness.
The task content must never be treated as the complete send list. Test PRICE task with DESIGN + PRICE asks, DESIGN task
with other asks, task decline/cancel, and task completion while another non-task content remains.

### 6. IMPORTANT — `askedFor = []` needs an explicit compatibility mode for existing open production deals

**What's wrong**

Leaving old deals empty and showing no warning is correct for resolved historical deals: a past send does not prove
what was asked. But production also contains live open deals whose current `nextActionKind` already says “Poslať cenu”,
“Poslať návrh”, or “Poslať úvodný email”. An empty checklist must not erase or change those existing obligations.
The draft does not say how new send-completion logic behaves for such deals.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:126-155,176-199`
- `components/pipeline/OfferSentDialog.tsx:72-83,137-145` — today's prefills/completion still fall back to the stored
  step and pending task results.
- `context/domain/database-map.md:50-68` — the current next step is an existing operational fact.

**Concrete failure scenario**

At rollout an old active deal has `SEND_QUOTE`, no task, and `askedFor = []`. The SR opens it and sends the price. If
Wave 5's new completion rule requires the last requested row to become checked, it may keep `SEND_QUOTE` forever. If
the UI renders only the new checklist, it shows no content beside a real send step. A bulk backfill of every old send as
an ask would be equally wrong.

**Why it matters**

Thousands of old/resolved rows are safe with an empty default, but even a small number of active rows must remain
workable on deployment.

**Suggested fix**

Define a legacy-uninitialized mode. Because every new positive Wave 5 call requires at least one ask, an empty list can
mean “unknown old intent” unless the final model uses a more explicit marker. In that mode:

- preserve today's next-step prefill/completion behavior;
- do not claim that the client asked for anything and do not show asked-vs-got warnings;
- keep task/pending-result behavior;
- transition to normal Wave 5 behavior when a user explicitly records/edits the current asks.

Alternatively, inventory only **open** production deals and backfill an explicitly marked operational obligation from
their current send step, without rewriting resolved history. Specify and test the chosen path on the production clone.

### 7. BLOCKER FOR PRODUCTION — §6's “No conversion” sentence can be misread as cancelling the required old-send conversion

**What's wrong**

“Old deals: `askedFor` is empty … No conversion” is correct only for **client asks**. It is not correct for what clients
received. The chosen rollout still requires the old about-us, exact-price, design, and manually identified cenník facts
to be converted into canonical `OFFER_SENT` rows before obsolete columns are removed. Wave 5 depends on those canonical
rows for price visibility and asked-vs-got comparisons.

The new clarification that old “Cenová ponuka” represented an exact price strengthens the likely PRICE mapping, but it
does not make the mutable current `Lead.price` a historical snapshot or remove the need to inventory undo/date/channel
exceptions on a production duplicate.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:185-199`
- `prisma/schema.prisma:105-121` — old frozen columns and new canonical summaries are different fields with different
  semantics.
- `context/domain/db-changes.md:210-245,258-310,312-325` — the approved conversion/rehearsal/contraction contract.

**Concrete failure scenario**

An implementer reads “No conversion”, adds `askedFor` and REVIEW, and later deploys the contracted schema without
running the separately required send conversion. An old client who received an exact price then appears as “Klient
cenu ešte nevidel”; deleting `quoteSentAt`/`priceDisclosed` destroys the only remaining evidence.

**Why it matters**

This is the main production data-loss boundary. Wave 5 will be the first feature to rely directly on the canonical
receipt projection for every deal.

**Suggested fix**

Write the separation directly into §6:

- **Asked history:** do not infer it for historical deals; `askedFor`/the request ledger starts empty unless an active
  compatibility rule is explicitly approved.
- **Received history:** still run `db-changes.md` §3.3. Confirmed old CP/exact-price evidence becomes an
  `OFFER_SENT` with `contents: [PRICE]` and a verified amount/date/channel; about-us becomes ABOUT_US; sent návrh becomes
  DESIGN with the correct design identity; the explicit 20–30 cenník recipients add PRICELIST to the correct same email
  event.
- Never map old sent evidence to `ClientAsk.PRICE`, and never reuse the old boolean/date columns as the permanent new
  source of truth.

Keep the fresh-production-duplicate inventory, exception file, idempotent rerun, reconciliation, backup, and
non-additive contraction gates. The user's description is the business mapping hypothesis; the duplicate establishes
the actual rows.

### 8. IMPORTANT — the stored headline is not actually derived, and the transition policy is incomplete

**What's wrong**

The draft says the checklist/headline is derived and therefore “can never be wrong”, but the headline is still stored
in `Lead.nextActionKind`. It also explicitly allows the SR to choose CALL while unsent asks remain, so the headline
cannot simply equal the dominant outstanding content at all times. No rule says when the system may rewrite the stored
step and when it must preserve the user's plan.

Edits, corrections, task transitions, and partial sends can therefore leave different screens with different answers.
Current correction code intentionally recomputes receipt summaries but never touches the next step.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:80-84,109-111,126-155,194-218`
- `lib/domain/offerMutations.ts:211-229` — correcting an offer does not restore/change a step.
- `lib/domain/taskMutations.ts:55-58` — ending a task only dates the already stored kind.
- `lib/queries/pipeline/index.ts:54-74,113-145` — pills, ordering, and “Na dnes” use the persisted step and task lock.

**Concrete failure scenario**

The client asks for DESIGN + PRICE. The SR sends DESIGN, so the automatic headline should shrink to PRICE. She then
changes the step to CALL for a promised appointment; the PRICE warning correctly remains. Later she crosses out the
DESIGN send as a mistake. Should the system overwrite CALL with SEND_DESIGN, leave CALL and show both warnings, or only
change the headline if it is currently a send step? The proposal does not decide.

Removing DESIGN with the pencil has the inverse problem. If a DESIGN task is open, does the edit leave the task and
lock in place, offer to cancel it, or cancel it automatically? Automatic cancellation would violate the task boundary;
leaving it silently is confusing.

**Why it matters**

The stored kind controls list membership, counts, sorting, urgency, and the server's step-lock/I10 rules. “The checklist
is right” is not enough if the headline and filters drift.

**Suggested fix**

Add a transition table for: first positive call, later ask addition, pencil replacement/removal, partial email send,
phone price, send correction, task create/finish/decline/cancel, manual replan, close, and reopen. A coherent policy
would be:

- the projection always owns checklist rows and warnings;
- a new ask suggests/installs the dominant send step unless a lock requires fact-only behavior;
- automatic shrinking/expansion may update the stored kind only while the current step is a system send step or task
  lock; a deliberate CALL/WAIT/CUSTOM plan is preserved and warnings remain;
- editing an ask never silently cancels manager work; the UI explains the still-open task and offers the existing
  explicit cancellation path;
- corrections revive the checklist but follow the explicit stored-step policy rather than silently rewriting later
  work.

Whichever policy is chosen, one server operation must calculate it under the Lead lock; UI defaults are not the
invariant. Add TypeScript/SQL parity tests anywhere the projection is copied into list SQL.

### 9. IMPORTANT — first-call revert and later correction semantics do not include the new request summary

**What's wrong**

The positive first call will write `askedFor` in the same business transaction. Reverting that call currently restores
the lead to call stage and clears the handoff/step, but the proposal does not require it to clear/restore the new ask
data. A stale ask would then survive on a call-stage contact and be merged into the next first call.

Later call/request corrections are also undefined. Crossing out a `CLIENT_REPLIED` currently does not undo later work.
If its `meta.asked` added PRICE, the stored current ask list could continue to contain PRICE after the source contact is
crossed out.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:107-111,189-195,228-233`
- `lib/commands/history.ts:93-117` — first-call revert clears call/deal fields but has no future ask restoration.
- `lib/domain/offerMutations.ts:209-229` — correction deliberately changes only the corrected fact/receipt summaries.

**Concrete failure scenario**

A telesales person accidentally selects PRICE + DESIGN and hands the contact off. The result is reverted before any
other change. The contact goes back to `/calls`, but `askedFor` remains. A later real first call records only INFO; a
union update leaves PRICE + DESIGN in the deal and creates false warnings/tasks.

**Why it matters**

The current first-call revert promises to undo the handoff completely while nothing else touched the lead. Wave 5 must
not leave half of that transaction behind.

**Suggested fix**

For first-call revert, restore the exact pre-call request state; for a call-stage lead this will normally be the empty /
uninitialized state. Include it in the state-match and concurrency tests.

For later corrections, choose one explicit rule consistent with the existing “do not rewrite later work” principle.
The safest is: crossing out the contact does not automatically remove current asks; the UI points to the “Chceli”
editor when necessary, and that separate keyed edit records the correction. If automatic reversal is desired, it must
prove no later request/edit touched the same content before removing it.

### 10. IMPORTANT — the `ASKED_CHANGED` data/command contract is still an unresolved question, not part of the schema plan

**What's wrong**

The preferred answer in Q5 is a new `ActivityType.ASKED_CHANGED`, but §6 does not list that enum addition and does not
define its metadata, category, permission, freshness, or idempotency. Two implementers could record a NOTE, mutate only
the array with no history, or create a new activity that accidentally counts as “Naposledy”.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:83-84,189-199,235-245`
- `prisma/schema.prisma:177-236` — current Activity shape and enum.
- `context/project-overview.md:101-115` — every existing-Lead mutation requires the lock/revision/retry contract.
- `lib/domain/offers.ts:216-217` — “Naposledy” is an explicit type allow-list today.

**Concrete failure scenario**

The SR removes DESIGN because the client no longer wants it. A simple Lead update succeeds twice from two tabs and
does not explain who changed it or what was removed; or an implementation uses `NOTE`, which falsely moves the last
client-contact line. A concurrent call adds PRICE while the pencil submits a stale replacement list and one change is
lost.

**Why it matters**

This is the only repair/removal path for incorrect and withdrawn asks. It must have the same audit and concurrency
quality as other deal mutations.

**Suggested fix**

Resolve Q5 before freezing the spec and add the actual schema ID (for example S-18) if a new enum value is chosen.
Define a strict payload and activity meta such as canonical `before`, `after`, `added`, `removed`, reason/source, and
`fp`; use `requireDealWork`, `withLockTx`, `expectedRevision`, `runKeyed`, named fields, and exactly one revision bump.
Decide whether only the owner and manager may edit (recommended under current access rules), and whether closed deals
are manager-only/read-only. The new activity should be visible in history but excluded from last-touch. Add a two-tab
replacement-vs-add race test.

### 11. IMPORTANT — “the call statistics keep working” is true only for routing compatibility, not intent statistics

**What's wrong**

One `Activity.outcome` can hold only one value. The proposal maps a multi-selection to the dominant existing outcome:
DESIGN wins over PRICE, otherwise EMAIL. That keeps handoff and broad workflow compatibility, but any statistic that
counts `WANTS_QUOTE` or `WANTS_DESIGN` no longer counts literal client demand correctly.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:174-183`
- `prisma/schema.prisma:177-188,238-248` — one nullable outcome per activity.
- `lib/domain/leadFlow.ts:13-30,154-170` — the current first-call/follow-up vocabularies are single outcomes.

**Concrete failure scenario**

Ten clients ask for PRICE + DESIGN. Every call stores `WANTS_DESIGN`; a report over call outcomes says zero asked for a
price. The UI worked, but management draws the wrong conclusion.

**Why it matters**

The feature explicitly wants to measure what clients asked for. Calling the old statistics correct invites future code
to query the wrong source.

**Suggested fix**

State that `CallOutcome` remains a **compatibility/routing outcome only**. All new demand statistics must read the
append-only ask evidence (`Activity.meta.asked` or the request ledger chosen for finding 2), not the dominant outcome
or only the current `Lead.askedFor` summary. Reverted activities must be excluded. Add a test proving that a combined
PRICE + DESIGN call remains one call but contributes to both ask counts.

### 12. MINOR — the send dialog has no general note in which to explain an unticked requested item

**What's wrong**

The proposal says the rep may untick a requested item and explain it in the note. The current dialog has only the price
breakdown and task-result dismissal/cancellation reasons; it has no general email/send note. The generated activity
note describes contents and is not user-editable.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:100-105`
- `components/pipeline/OfferSentDialog.tsx:72-99,108-145,300-323,430-452`
- `lib/domain/offerMutations.ts:160-181` — `Activity.note` is generated by `offerNote`.

**Concrete failure scenario**

PRICE and DESIGN are pre-ticked. The SR sends only PRICE because the návrh is not ready. The proposal tells her she can
explain the untick, but there is nowhere to type that explanation unless she incorrectly changes the price breakdown
or dismisses a manager result.

**Why it matters**

It is misleading UX and could encourage users to put unrelated text into the price note.

**Suggested fix**

Prefer the simpler behavior: remove “and explain in the note”. Unticking leaves the requested item visibly outstanding,
which already explains the state without extra form-filling. Add a general send note only if there is a real retrieval
place and use case for it; routine correspondence is intentionally not tracked.

### 13. DESIGN CHOICE, NOT A BUG — `NOTHING_SPECIFIC` adds a distinct statistic but no distinct work

**What's disputed**

“Info / ukážky” and “Nič konkrétne – len email” currently lead to the same basic email and likely the same satisfaction
rule. Keeping them separate is valid if Michal wants to measure a real request versus a polite brush-off. If nobody will
use that distinction, it adds an exclusive mobile choice and mapping complexity without changing the work.

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:39-48,57-68,176-180,239-243`

**Concrete scenario**

The client says “pošlite mi niečo”. One telesales person chooses INFO; another interprets the same sentence as
NOTHING_SPECIFIC. Both produce the same email, but reporting treats them differently.

**Suggested decision**

Keep it only if the distinction will be reviewed as a statistic or coaching signal. If kept, provide one sentence of
selection guidance and the exact satisfaction mapping from finding 3. Otherwise use INFO for both and put the nuance in
the call note. This is a product preference, not a correctness blocker by itself.

## Required acceptance matrix before implementation

The final proposal should name tests for at least these cases:

1. First call with every single ask, PRICE + DESIGN, and all compatible asks; reordered arrays are the same payload,
   changed arrays under the same key conflict.
2. NOTHING_SPECIFIC exclusivity and its exact email satisfaction rule.
3. PRICE by PHONE: client knowledge updates, written-send obligation follows the chosen product rule.
4. Old PRICE already sent → new PRICE request; old design already sent → new DESIGN request.
5. Partial sends in both orders, extra unasked contents, corrections that revive a row, and two tabs sending overlapping
   subsets.
6. Existing production-style open deal with empty/uninitialized asks and each current SEND_* step.
7. Current Wave 3 PRICE task on a deal asking PRICE + DESIGN, and DESIGN task with INFO/CENNÍK/PRICE also outstanding;
   finish, decline, cancel, overlap, and send while locked.
8. Add/remove asks while a task is open; no silent task cancellation.
9. First-call revert clears/restores request state; later corrected contact follows the explicit non-rewrite rule.
10. Owner/manager scope, another rep rejected as NOT_FOUND, closed/reopened deal, deactivated owner, and exact one-bump
    behavior for each mutation.
11. Checklist/list warning/headline/count parity, including any TypeScript rule duplicated in SQL.
12. Production-clone rehearsal: old about-us, exact-price, cenník and návrh combinations; no inferred asks; no duplicate
    `OFFER_SENT`; canonical summaries and price snapshots reconcile; active old deals retain workable steps.

## Final recommendation

**Keep the product concept, but rethink and freeze the request/obligation projection before coding.** The smallest safe
version is not “one more array plus comparisons”. It needs an exact mapping, temporal request identity, separate client
knowledge versus email obligation, a compatibility rule for existing open deals, and explicit integration with today's
task/step transitions. Those can all be implemented additively. The later removal of old production columns remains a
separate, deliberately non-additive migration after canonical conversion and duplicate-database rehearsal.

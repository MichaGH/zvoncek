# Wave 5 implementation review — R02

Date: 2026-09-20  
Scope: verification of the R01 fixes and response, followed by a fresh review of the Wave 5 request/receipt workflow,
the redesigned interaction sheet, SMS price + keep-step behavior, manager status paths, design tracking, corrections,
migration code, documentation, and Wave 3 integration.  
Review type: implementation review. No application or context file was changed; this review record is the only file
added.

## Verdict

**Changes requested, but no new rollout blocker was found.** Claude correctly fixed the five substantive R01 findings:
the cenník migration now produces a linked `SENT` receipt, same-call phone prices derive the step after reconciliation,
the action sheet withdraws open asks on snooze/close, offer defaults contain only asked content, and a proposal sent
without a `Design` row can now be recorded. The focused tests and the complete regression suite pass.

The fresh review found four important edge paths not covered by those tests. A manager can still snooze from the detail
without withdrawing open asks; the untracked-design summary breaks as soon as any Design row (including a deleted one)
exists; correcting an SMS does not correct the price receipt created from that same SMS; and the new keep-step choice is
preselected even when the SMS price has just completed a `SEND_QUOTE` step. The last item is a workflow/design defect in
the newly accepted behavior, not a disagreement between the code and its current documentation.

The known Wave 4 limitation is deliberately outside this review: manager help still cannot represent and partially
return combined PRICE + DESIGN work. Nothing below asks Wave 5 to implement that feature.

## Findings

### 1. IMPORTANT — manager-side snooze still bypasses the new withdraw-on-snooze invariant

**Where**

- `components/pipeline/DealDetail.tsx:202-210` opens the status confirmation for `SNOOZED` only when an open manager
  task exists. Open client requests alone do not open it; the status command is sent immediately without `withdraw`.
- `components/pipeline/DealDetail.tsx:217-224` does include `withdrawFor(...)` when a confirmation happens, but
  `components/pipeline/DealDetail.tsx:886-889` requires a non-empty reason only for a closing status, not for
  `SNOOZED`.
- `lib/domain/dealMutations.ts:439-453` changes an open deal to `SNOOZED` without calling
  `withdrawOpenOnLeave()`. It silently ignores `opts.withdraw` if a caller supplied it.
- `lib/commands/pipeline.ts:70-92` accepts and fingerprints `withdraw` for every status, so this is not rejected as an
  invalid payload at the command boundary either.
- `context/features/01-salesrep/wave-5-workflow.md:156-163` and `context/app-workflow.md:248-254` require every snooze
  with outstanding client work to name it, require a reason, and withdraw it atomically.

**Concrete failure scenario**

A client has open PRICE + DESIGN requests and no manager task. Michal opens the deal detail and changes the status to
`SNOOZED`. There is no warning and no reason field. The deal becomes snoozed while both requests remain `OPEN`. If an
open manager task happens to exist, the confirmation does send the request IDs, but the domain function still ignores
them; a blank reason is also allowed by the button.

**Why it matters**

The same business operation has opposite semantics depending on which screen performed it. The rep's action sheet
records that the promised work will not be sent; the manager's status selector silently parks it. The server does not
enforce the advertised invariant, so a future caller can repeat the bypass even if the UI is repaired.

**Suggested fix**

For the `SNOOZED` branch of `changeDealStatus`, call `withdrawOpenOnLeave()` before changing the status, under the same
Lead lock. In the detail, open the confirmation when `value === "SNOOZED" && openAsks.length > 0`, list the contents,
and require the reason exactly as the action sheet does. Reject a `withdraw` payload for statuses that do not consume
it. Add a `w5ManagerSnooze` test covering no payload, blank/partial/stale IDs, success, one revision/audit row,
idempotent retry, and snooze with an open task plus open asks.

### 2. IMPORTANT — an untracked proposal stops contributing to `Lead.designSentAt` when any Design row exists

**Where**

- `lib/domain/offerMutations.ts:42-53` loads every Design row, including deleted rows, while only non-deleted rows can
  contribute a tracked sent date.
- `lib/domain/offerMutations.ts:56-63` chooses either tracked designs or the untracked receipt based on
  `designs.length`. It never combines the two sources.
- `lib/domain/offerMutations.ts:174-181` correctly allows an untracked receipt when there is no **non-deleted** Design,
  which is a different condition from `designs.length === 0` used by the recomputation.
- `lib/commands/tracking.ts:112-117` recomputes immediately after deleting a Design, exposing the mismatch.
- `prisma/backfill/check-concurrency.ts:3757-3810` tests only a deal with literally zero Design rows; it does not cover
  deleted rows or a Design created after an untracked receipt.

**Concrete failure scenarios**

1. A legacy deal has one deleted Design row. Because there is no non-deleted Design, the server accepts “Návrh — bez
   záznamu v systéme” and resolves the DESIGN request. `recomputeOffers()` sees `designs.length === 1`, ignores the
   untracked receipt, and leaves `Lead.designSentAt` null immediately.
2. A PDF/untracked proposal was validly sent and `designSentAt` was set. Later Michal creates a tracked Design for a new
   version. The next unrelated offer recomputation sees that Design row, ignores the still-valid untracked send, and
   clears the fact that the client already received a proposal. Deleting that new Design has the same effect.

**Why it matters**

The canonical `OFFER_SENT` history and request row say DESIGN was received, while the Lead summary and filters say it
was not. This is exactly the summary-versus-ledger drift Wave 3a/Wave 5 were designed to prevent, and it can appear
after an ordinary later lifecycle action.

**Suggested fix**

When canonical design evidence owns the summary, compute `Lead.designSentAt` as the latest valid date across both:
non-deleted tracked designs and valid untracked-design receipts. Preserve the untouched legacy value only when there
is neither any Design history nor any untracked receipt history. A deleted Design must not suppress a valid untracked
receipt. Add tests for (a) only deleted Design rows before the untracked send, (b) a Design created after the untracked
send, (c) that Design then deleted, and (d) correction of the untracked receipt while another unsent Design exists.

### 3. IMPORTANT — crossing out an SMS leaves the price from that same SMS active

**Where**

- `lib/commands/dealWork.ts:265-317` creates an `SMS_SENT` activity and then a linked `OFFER_SENT` with
  `callActivityId = SMS_SENT.id`, `channel = PHONE`, and `via = SMS`.
- `components/pipeline/DealDetail.tsx:683-755` shows both rows as correctable; the price row is visually presented as
  “↳ Cena uvedená v SMS”.
- `lib/domain/offerMutations.ts:264-283` recomputes offers and requests only when the corrected row itself is
  `OFFER_SENT`. Correcting the parent `SMS_SENT` takes the generic branch and only bumps the Lead revision.
- `prisma/backfill/check-concurrency.ts:3843-3893` verifies creation and keep-step behavior, but has no linked
  correction case.

**Concrete failure scenario**

An SR records the SMS “Cena je 990 €” and checks that the SMS contained the concrete price. The client did not actually
receive the SMS, so she opens history and crosses out the `SMS_SENT` row with reason “neodoslané”. The visible SMS is
now corrected, but its linked price receipt remains valid: the PRICE request stays `SENT`, the card still says “Klient
videl 990 € (SMS)”, and the next workflow assumes the client knows the amount.

**Why it matters**

The linked child fact cannot truthfully survive a correction saying its carrier never happened. The arrow in history
makes the two rows look like one event, so expecting users to discover and correct both independently is unsafe and
easy to miss.

**Suggested fix**

Make correction of an `SMS_SENT` row atomically cross out any valid `OFFER_SENT` rows whose `meta.callActivityId`
points to it, then recompute offer summaries and reconcile requests once before the single Lead revision bump. Keep
the reverse direction independent: correcting only the price can leave the SMS text in history. Add a test proving
that correcting the SMS clears/recomputes `clientPrice` and `offerPriceAt`, reopens the PRICE request when appropriate,
does not create a second revision, and loses correctly against a concurrent second correction.

### 4. IMPORTANT (workflow/design) — “keep current step” is unconditional even when the SMS just completed that step

**Where**

- `components/pipeline/InteractionSheet.tsx:1024-1033` preselects keep-current for every SMS whenever any current step
  exists, including after the user entered a price in that SMS.
- `components/pipeline/InteractionSheet.tsx:1207-1217` labels the kept step from `nextActionNote` / the enum label,
  not from the Wave 5 combined `stepHeadline`.
- `lib/commands/dealWork.ts:158-171,320-323` deliberately treats `keepStep` as fact-only and returns before the normal
  system-step refresh.
- `lib/domain/clientRequests.ts:107-113` falls back to the stored step when no request remains. A preserved
  `SEND_QUOTE` therefore continues to display as a price-send step after PRICE was satisfied.
- `prisma/backfill/check-concurrency.ts:3872-3893` captures the Lead state before the second, price-bearing SMS and
  checks only that `withPrice` returned OK. It does not assert the step or outstanding state after that price SMS.

**Concrete failure scenario**

The current step is `SEND_QUOTE` because the client is waiting for an exact price. The SR chooses “Poslali sme SMS”,
checks “V SMS bola konkrétna cena”, enters 990 €, and continues. “Ponechať aktuálny krok” is preselected, so the natural
one-click save records that the client saw 990 € and closes the PRICE request, but leaves `SEND_QUOTE` unchanged. The
deal still tells the SR to send the price she has just sent.

A second clarity problem appears with combined work: a stored `SEND_DESIGN` can visibly mean “Poslať návrh + cenu +
cenník”, but the keep card can show only the stored note “Poslať návrh”. The user cannot see from the selected option
that all three pieces are being preserved.

**Why it matters**

The keep option itself is useful and matches Michal's example: an informational SMS such as “email sme poslali” should
not destroy an existing follow-up appointment. The defect is the unconditional default and incomplete label. It makes
the easiest path wrong precisely when the SMS records fulfillment of the current system send step.

**Suggested fix**

Keep the option, but distinguish manual plans from system send steps. It is safe to preselect for CALL,
WAITING_FOR_CLIENT, CUSTOM and similar deliberate plans. When the SMS price satisfies a current `SEND_QUOTE` request,
do not preselect keep; derive from what remains or require the user to choose the next plan when nothing remains. If
keeping a completed system step is still allowed as an explicit exception, show a warning rather than making it the
default. Display `D.stepHeadline ?? D.nextActionNote ?? NEXT_ACTION_LABEL[...]` in the keep card so combined work is
named accurately. Extend the test with PRICE-only/SEND_QUOTE, PRICE + DESIGN, and a manual CALL appointment.

### 5. MINOR — the Wave 5 proposal's supersession note still describes the pre-R01 manager behavior

**Where**

- `context/features/01-salesrep/wave-5-proposal.md:478-482` says manager detail closing is still an open Q2 and that the
  old bullets remain authoritative there.
- `context/features/01-salesrep/wave-5-proposal.md:484-491` then says status changes never withdraw requests.
- `.ai/reviews/01-sales-rep/W5/implementation/R01-response.md:154-157` records Q2 as answered and implemented for
  manager LOST/UNREACHABLE.
- `context/app-workflow.md:248-254` correctly documents the new manager LOST/UNREACHABLE behavior.
- `prisma/backfill/check-concurrency.ts:3385-3410` still describes “closing leaves requests untouched”, although the
  test's open-request case is specifically `WON` (the intentional exception).

**Concrete failure scenario**

The next agent reads the feature proposal before changing manager status behavior and concludes that manager
LOST/UNREACHABLE must preserve open rows. That is now false and could undo the accepted R01 fix. The generic test name
reinforces the wrong conclusion even though its assertions cover WON.

**Why it matters**

This is documentation/test-description drift, not a runtime failure. It is still risky because the proposal is the
design record used for future Wave 4 integration.

**Suggested fix**

Replace the temporary supersession note with the final matrix: action-sheet snooze/close withdraws; manager
LOST/UNREACHABLE withdraws; WON deliberately leaves open history; manager SNOOZED should follow the snooze rule after
finding 1 is fixed. Rename the W5-9 description to state that it tests WON specifically.

## Workflow verification

### Client asks for several things

The call/reply flow works as intended. The user chooses multiple contents once; same-call PRICE is linked and resolved;
the server derives the remaining combined send step. Repeated asks stay separate in history and collapse to one work
row. The Wave 4 task limitation remains visible but does not corrupt Wave 5 state.

### Sending and partial sending

Asked-only defaults, partial receipts, combined headlines, correction/reopen of request rows and manager-result
integration all pass. Untracked DESIGN now has a usable UI and server path. Finding 2 is its missing mixed-lifecycle
case.

### SMS and current step

The phone-sized preview is readable and has no navigation dead end. A normal SMS can preserve an appointment or other
current step without a date re-entry, which is a good fit for “email sme poslali”. Price-bearing SMS correctly creates
the linked client-knowledge receipt. Findings 3 and 4 are the two missing combinations between those otherwise sound
features.

### Snooze, close and reopen

The action sheet and manager LOST/UNREACHABLE paths now require exact open request IDs and a reason, reject stale tabs,
and leave withdrawn rows withdrawn on reopen. WON intentionally keeps its open rows and revives their send step on
reopen. Only the manager detail's direct SNOOZED path remains inconsistent (finding 1).

## UI assessment

The desktop and 390 × 844 phone layouts remain clear and usable. The solid icon colours are high-contrast and the
selected states are easy to scan; they are slightly playful, but that is a visual preference rather than a usability
bug. The SMS “Ponechať aktuálny krok” tile is understandable, but it must show the combined dynamic headline and should
not be the automatic choice after that same SMS completed a send-price step.

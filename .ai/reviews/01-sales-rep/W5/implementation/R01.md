# Wave 5 implementation review — R01

Date: 2026-09-20  
Scope: the shipped Wave 5 request ledger, first-call and follow-up workflows, offer receipts, list/detail projections, rollout script, current interaction-sheet redesign, and their integration with Wave 3.  
Review type: implementation review. Application/context files were not changed; this review record is the only file added.

## Verdict

**Changes requested.** The central implementation is sound: access remains server-side, writes use the Lead lock and revision/idempotency rules, the request/receipt reconciliation is centralized, and list/detail/TODAY parity passed. The focused Wave 5 concurrency suite passed all 13 selected groups at 100 iterations.

There is one production-rollout blocker: the explicit legacy cenník list is inserted as work still owed even though the documentation defines those leads as recipients. There are also four important current-workflow gaps: the new sheet can preserve a send-price step automatically after that same call already satisfied the price request, the newer close/snooze contract is not implemented, the send dialog preselects unasked content, and a design receipt cannot be recorded without a `Design` row despite the interaction contract requiring that legacy/PDF path.

The known Wave 4 limitation is deliberately outside this review: one manager request cannot yet represent and partially resolve combined PRICE + DESIGN work. F1 (`/calls` self-handoff toast) and F2 (`SEND_DESIGN` not appearing in “Na dnes”) also remain the already-recorded follow-ups, not new findings here.

## Findings

### 1. BLOCKER — the production cenník backfill turns confirmed recipients into open work

**Where**

- `prisma/backfill/2026-09-wave5-requests.ts:157-170` inserts every ID supplied through `--pricelist-leads` as `PRICELIST`, state `OPEN`, origin `MIGRATED_RECEIPT`, with no receipt link.
- `context/domain/db-changes.md:241-245` says the manually reviewed cenník recipients must get `PRICELIST` added to the same canonical email receipt.
- `context/domain/db-changes.md:398-408` says old content the client received becomes a `SENT` request with origin `MIGRATED_RECEIPT`.
- `prisma/backfill/check-concurrency.ts:3459-3488` tests only generic `migrationKey` idempotency; it does not execute or verify the `--pricelist-leads` path.

**Concrete failure scenario**

Michal identifies 25 old leads that genuinely received a cenník and supplies those IDs during the production-clone rehearsal. The script creates 25 `OPEN` requests. After deployment, each deal says the client still needs a cenník; an open deal can move to “Poslať cenník”, and a rep can send it again. The row simultaneously claims `MIGRATED_RECEIPT` provenance and has no receipt that resolved it.

**Why it matters**

This reverses the meaning of verified live data and creates false outstanding work during the migration. It blocks production rollout even though it does not block continued test-branch work.

**Suggested fix**

Make the manual input identify the exact canonical `OFFER_SENT` activity (preferably `leadId + activityId`, not only a lead ID), add `PRICELIST` to that activity's contents in the preceding offer migration, then let the normal receipt backfill create a linked `SENT` request. If the Wave 5 script keeps a manual mode, it must create/verify `SENT`, `resolvedAt`, `resolvedById`, and `resolvedActivityId` from an existing valid receipt and refuse an ambiguous lead. Add a migration test that runs this actual branch twice and verifies that no `PRICELIST` row is left open.

### 2. IMPORTANT — same-call phone price is resolved, but the UI can still force the old send-price step

**Where**

- `components/pipeline/InteractionSheet.tsx:1025-1047` derives `nextWanted` from the old outstanding set plus every newly selected request and submits it as an explicit `nextKind`.
- `lib/commands/dealWork.ts:251-285` correctly creates the requests and resolves the same-call PRICE request through the linked phone `OFFER_SENT` activity.
- `lib/commands/dealWork.ts:318-324` recomputes the default only when `input.nextKind` is absent, so the UI's pre-reconciliation value wins.
- `context/features/01-salesrep/wave-5-workflow.md:14-20` says a send step is derived from what is still outstanding, not selected separately.

**Concrete failure scenario**

An SR records “Povedal/a som cenu 1,200 €”, then chooses “Chcú niečo poslať” and selects PRICE + INFO. The server correctly marks the new PRICE request as `SENT` by that phone receipt; only INFO remains open. The client, however, submitted `SEND_QUOTE` because PRICE dominated the pre-save selection. The deal therefore shows “Poslať cenu” plus a warning that info is still missing instead of the derived “Poslať info”. PRICE alone leaves “Poslať cenu” even though no request remains.

Keeping written confirmation after a phone quote can be a valid manual decision, but this flow never asks the user; it silently treats an automatic pre-save projection as an explicit override.

**Why it matters**

The stored step and request ledger disagree immediately after a normal single transaction. The rep can send the wrong content or must repair the step manually. The current W5 tests cover same-call linking and explicit step precedence independently, but not this real UI payload combination.

**Suggested fix**

For the “Chcú niečo” automatic path, do not send a derived `nextKind`. Let `logFollowUpAs` add the requests, record/reconcile the phone receipt, then derive the step from the final outstanding set in the same locked transaction. If written confirmation of a phone price is wanted, make that a separate explicit choice with clear wording. Add cases for phone PRICE + asked PRICE, PRICE + INFO, PRICE + DESIGN, and a retry with the same key.

### 3. IMPORTANT — the implemented close/snooze behavior contradicts the newer Wave 5 workflow contract

**Where**

- `context/features/01-salesrep/wave-5-workflow.md:156-163` requires snooze or close with outstanding content to list it, require a reason, and withdraw every open request.
- `components/pipeline/InteractionSheet.tsx:399-416` only detects returned Wave 3 task items, not open `LeadRequest` rows.
- `components/pipeline/InteractionSheet.tsx:463-487` deliberately omits `asked`/dismissal data on close and has no request-withdrawal payload.
- `components/pipeline/InteractionSheet.tsx:1260-1289` lets a deal with client-request work be snoozed without acknowledging that work.
- `components/pipeline/InteractionSheet.tsx:1312-1343` warns about tasks/pending results only; the close reason remains optional and open client requests are not shown.
- `lib/commands/dealWork.ts:325-338` closes pending manager results but leaves `LeadRequest` rows untouched.
- `prisma/backfill/check-concurrency.ts:3406-3410` still asserts the older, opposite rule: closing leaves requests open and reopening revives the send step.
- `context/features/01-salesrep/wave-5-proposal.md:557,654` also retains that older rule.

**Concrete failure scenario**

A client asked for a price and návrh. Before either is sent, the SR chooses “Ozvať sa o 6 mesiacov” or closes the deal as not interested. The UI neither names the two promises nor asks why they are being abandoned. Both requests remain `OPEN`. On snooze they are hidden behind the parked deal; on close they later reappear as active send work if a manager reopens it.

**Why it matters**

This can silently lose promised work now and unexpectedly resurrect abandoned work later. More importantly, two active feature documents and the automated test define opposite business semantics, while the newer workflow declares itself implemented.

**Suggested fix**

First make the product decision authoritative in one place. If the newer workflow is the accepted rule, submit the exact currently open request IDs plus a mandatory reason, withdraw them under the same Lead lock and transaction as snooze/close, and log the audit. Do not trust a client boolean such as “withdraw all”. Add tests for snooze, LOST, UNREACHABLE, idempotent retry, a stale row changed in another tab, and reopen. If dormant/open-on-close is actually intended, remove the contradictory promise from `wave-5-workflow.md` and explain the reappearance on reopen in the UI.

### 4. IMPORTANT — “Čo sme poslali” preselects content the client did not ask for

**Where**

- `components/pipeline/OfferSentDialog.tsx:85-101` preselects INFO and PRICELIST whenever each has never been sent, independently of `deal.asked`.
- `context/features/01-salesrep/wave-5-proposal.md:121-128` says asked-and-outstanding contents are preselected; extra contents may be added deliberately.
- `context/features/01-salesrep/wave-5-workflow.md:175-179` says the additive dialog preselects only what is outstanding.
- `context/app-workflow.md:191-195` instead says to preselect what was never sent, so the context itself is inconsistent with the newer contract.

**Concrete failure scenario**

The client asked only for a návrh. On a new deal, the rep opens “Poslali sme ponuku”; INFO and Cenník are already checked merely because neither was sent before, alongside the návrh. If the rep trusts the defaults and saves, the CRM permanently records that all three reached the client even when the email contained only the návrh.

**Why it matters**

Wave 5 exists to distinguish exactly what was requested and received. Aggressive defaults make a false receipt one ordinary click away and pollute later price/client-history decisions. “The first email often contains info” does not justify preselecting cenník on every first send.

**Suggested fix**

Preselect only current outstanding request/manager-result contents and the explicit entry point (for example, the particular návrh button). Leave unasked INFO/PRICELIST available but unchecked. If the company deliberately wants a standard first-email bundle, represent it as one explicit UI preset (“Prvý email: info + cenník”) rather than indistinguishable automatic ticks. Then reconcile `app-workflow.md` with the chosen rule and add a component/domain test for a DESIGN-only request on a never-contacted deal.

### 5. IMPORTANT — an untracked/PDF návrh cannot be recorded as sent, so its request can be stranded

**Where**

- `context/features/01-salesrep/wave-5-workflow.md:167-173` explicitly requires a plain “Návrh” choice when no `Design` row exists (legacy deal, PDF, or ordinary link).
- `components/pipeline/OfferSentDialog.tsx:94-101,126-132` includes DESIGN only when at least one design ID is selected.
- `lib/domain/offerMutations.ts:163-172` rejects DESIGN without at least one valid, non-deleted `Design` row.

**Concrete failure scenario**

An old/open deal has an outstanding DESIGN request, but the proposal was sent as a PDF or via an untracked link and no `Design` record exists. “Čo sme poslali” offers no selectable návrh. The rep cannot create a valid DESIGN receipt, so the request and derived “Poslať návrh” step cannot be completed through the promised workflow.

**Why it matters**

This is especially relevant to migrated production data: the ledger can represent that a návrh is owed, but the only command that can satisfy it requires a newer tracking model the old deal may never have had.

**Suggested fix**

Define a canonical untracked-design receipt. The safest shape is DESIGN content with an explicit `untrackedDesign: true`/label snapshot and no IDs, while keeping the existing ID validation whenever IDs are supplied. Do not update `Design.sentAt` when no design row exists. Show the plain option only when there is no usable design to pick, and test request resolution, correction/reopen, summaries, and migration compatibility.

### 6. MINOR — the post-click-through status files still say the rebuilt sheet is open/unverified

**Where**

- `context/features/01-salesrep/wave-5-followups.md:7-12` still marks F4 open.
- `context/progress-tracker.md:297-302` still says the complete phone/desktop human click-through is owed.
- `context/features/01-salesrep/wave-5-workflow.md:9-10` says the workflow is implemented on the current branch.

**Concrete failure scenario**

The next implementation/review agent cannot tell whether it should treat the current interaction sheet as accepted, still under redesign, or merely technically implemented. That is likely to cause the UI to be reworked again or known behavior to be dismissed incorrectly.

**Why it matters**

This is process/documentation drift rather than a runtime defect, but these files control what the next AI is allowed to assume.

**Suggested fix**

After Michal explicitly accepts the final click-through, close F4 with the accepted commit and record which phone/desktop paths were checked. Keep F1/F2 open. The sentence “I like the design” is enough to record visual acceptance, but behavioral acceptance should wait until findings 2–5 are resolved and clicked through.

## Workflow walk-through

### First call — client asks for multiple things

`/calls` correctly requires at least one requested content for `INTERESTED`, creates one request row per selected content, assigns the deal using the existing routing rules, and derives one stored kind with a combined visible headline. List/detail/TODAY parity passed. The known next step is Wave 4: combined PRICE + DESIGN manager work and partial return.

### Follow-up — client asks for more

The rebuilt sheet is substantially clearer: contact type, phone-price fact, client reply, multi-select requested contents, and planning are separated; the user no longer chooses fake enum combinations. Repeated asks correctly create repeated event rows and collapse into one outstanding checklist. Finding 2 is the exception where the pre-save UI projection overrides the final reconciled state.

### Sending some or all requested content

Partial sends, request reconciliation, corrections, and combined headlines passed the focused tests. The remaining workflow risks are the unasked defaults (finding 4) and the missing plain návrh path (finding 5).

### Snooze, close, and reopen

The code behaves consistently with the original proposal and its current test: requests remain open while closed and return on reopen. It does **not** behave as the newer implemented-workflow document says. This must be resolved as a product rule, not patched only in the UI.

## UI and colour assessment

The solid colour tiles are very readable and the meanings are consistent, but the saturation makes the dialog slightly playful; lowering the tile saturation one step would make it feel more like a professional admin tool without losing the useful contrast.

The current desktop and 390 px phone preview otherwise has good hierarchy, comfortable tap targets, clear selected states, and no obvious clipping or dead end in the primary contact → reply → requested-content path.

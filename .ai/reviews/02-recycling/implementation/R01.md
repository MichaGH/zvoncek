## Findings

### R01-01 — [P2] Preserve child timestamps when changing their leadId

**Locations:** `lib/domain/recycleMutations.ts:89` and `:92`; `prisma/schema.prisma:354` and `:551`.

**Requirement:** spec §3.1 and §4.4 promise that the previous round and everything attached to it are retained untouched, with the child rows re-pointed to the archive. The documented timestamp exception applies to the archive **Lead** row's `updatedAt`, not to the historical children.

`archiveRound` passes `{ data: { leadId: archive.id } }` to `leadRequest.updateMany` and `design.updateMany`. Both models have Prisma-managed `@updatedAt` fields. Prisma updates those fields as part of these writes, even though the business record did not change. The old timestamps are lost from both the live and archived state.

**Reproduction:** create a deal with a Design and LeadRequest whose `updatedAt` is `2020-02-03T04:05:06.000Z`; recycle it. In the final regression run, the archived Design had `updatedAt = 2026-10-25T19:34:42.862Z` and the request had `2026-10-25T19:34:42.803Z`. Their IDs survived, but their timestamps did not. This affects every recycled contact carrying either child type.

**Impact:** the promised historical snapshot is incomplete, and later previous-round views or investigations cannot recover the original modification dates from the archived records. The current child-ID-only assertions in `rc2Reset` cannot detect this.

**Repair:** re-point these children without triggering timestamp changes, for example with parameterized SQL that changes only `leadId`. Preserve each row's individual timestamp; replacing all timestamps with one captured value would also be wrong. No schema change is needed.

**Required verification:** snapshot every scalar property of every direct child before recycling and compare afterwards, allowing only `leadId` to differ. Include different non-null timestamps on multiple rows. The two timestamp assertions in `check-recycling-review.ts` must pass.

### R01-02 — [P2] Carry enough selected-row context to present the approved warnings

**Locations:** `components/admin/recycle/RecyclePanel.tsx:31`, `:60`, `:288`; `lib/queries/recycling/index.ts:215`; `lib/actions/recycling/index.ts:34`.

**Requirement:** spec §8 requires the confirmation to identify affected owners and warn about open client requests, including an unfinished návrh; Q9 also calls for a warning when deliberately recycling recently contacted candidates. The sticky selection summary is meant to include a bucket breakdown.

Selection retains only `{ expectedRevision, bucket }`. The first-N operation likewise returns only IDs, revisions, and buckets. The dialog consequently warns only from bucket counts: wrong numbers, active/sleeping deals, and scheduled calls. It cannot identify the owner, count selected open client requests, or detect recent contact. The sticky bar also has only the total selection count; its existing bucket breakdown appears only in the dialog.

**Browser reproduction:** created an isolated ACTIVE deal owned by Michal Chovanec with an OPEN DESIGN LeadRequest and no open manager task. Selected it and opened confirmation. The entire warning was:

> ⚠ 1 aktívnych obchodov – zmiznú z pipeline vlastníka.

The owner was unnamed and the unfinished design promise was omitted. Recycling succeeded, so that promise disappeared from current work and became visible only in the archive. See `evidence/R01-confirmation.jpg`.

**Impact:** these are precisely the forgotten promises the feature is intended to recover. With first-N selection over up to 500 contacts and several pages, the admin cannot rely on having inspected every row before the final action. The confirmation currently understates the consequences of the selection. An open LeadRequest is intentionally eligible; rejecting all such deals would contradict the approved design.

**Repair:** preserve a compact warning summary for selected rows, including first-N selections, or obtain a server-generated preview for the explicit selected IDs. Include per-owner affected-deal counts, outstanding request counts/content, and recent-contact warnings. Keep mutation input limited to the selected IDs and their original revisions. Render the required bucket summary in the sticky bar as well.

**Required verification:** select contacts across two pages and with first-N, including two different owners, an unfinished DESIGN request, a recent call, a bad number, and a scheduled callback. Assert exact summary counts and owner names; verify changing filters clears selection and an OPEN DealTask still blocks recycling on the server.

### R01-03 — [P2] Implement the approved filters for what clients still want

**Locations:** `lib/domain/recycling.ts:171`, `:188`, `:224`; `components/admin/recycle/RecycleFilters.tsx:135`; `lib/queries/recycling/index.ts:55`.

**Requirement:** spec §5.2 explicitly includes “Dostali / chceli”: received info/price/design, and an open client request for design/price/info.

The URL model has only `got`. Its options are `info`, `pricelist`, `price`, and `design`, all labeled “Dostali …”. The query filters those options solely through receipt-summary columns. OPEN requests are selected for row display, but are never used by a candidate filter. There is no UI control or parsed URL state for the “chceli” half of the requirement.

**Reproduction:** open the recycling page's “Klient” selector. It contains the receipt choices and no open-request choices. An ACTIVE deal with an open DESIGN request and no design receipt cannot be isolated as “chceli návrh”; choosing “Dostali návrh” excludes it.

**Impact:** the admin cannot find the promised-but-never-sent work described in spec §1 and §2.2 without manually scanning the candidate list. A received-design filter answers a materially different business question.

**Repair:** add explicit URL-backed open-request filters, at least for the approved INFO/PRICE/DESIGN cases, based on `LeadRequest.state = OPEN`. Use the same predicate in list, bucket counts, holders, and first-N selection. Keep received and outstanding requests distinguishable.

**Required verification:** fixtures with OPEN, SENT, and WITHDRAWN requests of the same content; multiple requests of one content; a contact that has received one design but has a later open design request; and an archived request. Verify matching IDs, counts, first-N order, and URL round trips.

### R01-04 — [P2] Do not link archived call-history entries to the archive's deal route

**Location:** `lib/queries/calls/history.ts:76`.

**Requirement:** spec §4.5 keeps archived calls readable with the live contact number and an old-round label; browsing the previous round's deal detail is explicitly out of scope in §12.

`canRevert` and `canEdit` correctly check `deletedAt`, but `leadHref` does not. An archived deal still has its old `pipelineEnteredAt` and `ownerId`, so an administrator, manager, or its former owner gets `/dashboard/pipeline/<archive-id>`. The detail query correctly excludes that hidden row and returns not found.

**Browser reproduction:** recycle the isolated ACTIVE deal `#8319`. In the caller-filtered call history, click “#8319 R02UImvo7tkou Active (1. kolo)”. The link points to the newly created archive ID and opens “404 — Stránka sa nenašla”. The added regression also reproduces the same problem from a genuine INTERESTED call followed by recycling.

**Impact:** the changed history display presents a working-looking navigation affordance that is guaranteed to fail for archived deals. Correct number/round rendering and hidden edit buttons do not make the link valid.

**Repair:** make archived/deleted history rows plain text unless a separately authorized working destination exists. Simply substituting the live ID is insufficient: after recycling the live contact is in the call stage and also has no deal detail.

**Required verification:** archive an interested first call and check history as the manager and former owner; the number and round stay correct, editing/revert remain unavailable, and there is no dead detail link. Preserve working links for current, non-deleted deals. The new archived-deal-link assertion must pass.

### R01-05 — [P2] Normalize the page after recycling reduces the number of pages

**Locations:** `components/admin/recycle/RecyclePanel.tsx:114`, `:250`; `app/dashboard/admin/recycle/page.tsx:26`; `lib/queries/recycling/index.ts:133`.

The successful mutation refreshes the current URL without adjusting `page`. The server still applies `(page - 1) * 100`, and pagination disappears whenever the new page count is one. An out-of-range page can therefore have an empty table and no previous-page control even though matches remain.

**Browser reproduction:** the isolated call-lost filter had 102 candidates over two pages. On page 2, selected its two remaining rows and recycled them. The URL retained `page=2`; the screen simultaneously displayed:

> Nájdené: 100 · vybrané: 0
>
> Nič nezodpovedá filtrom.

Both paging buttons were gone. The 100 remaining candidates were on page 1. See `evidence/R01-last-page.jpg`.

**Impact:** a normal batch workflow leaves the admin at a contradictory dead end. Further recycling requires changing a filter, manually editing the URL, or using first-N without seeing the returned rows.

**Repair:** normalize an out-of-range page to a valid page while retaining filters and sort. Navigating to page 1 after a successful recycle is a simple mutation-side fix; server-side page normalization should also handle lists shrinking due to another administrator's action.

**Required verification:** 102 → 100 candidates while on page 2; 201 → 200 while on page 3; and a concurrent list shrink before refresh. Remaining candidates must be reachable immediately and the empty-state wording must agree with the total.

## Verdict

**CHANGES REQUIRED before production — one item can make the feature fail completely in production.**

The data design is sound and well defended: the archive row keeps every column, every child row moves atomically, the
archive is invisible to every reader checked, the live row is a correct fresh contact, concurrency and double submits

- **R02-04 (P2, workflow):** nothing protects contacts who asked not to be called again.

### R02-01 — P1 — the recycle command can never finish in production if functions run far from the database

**Where:** `lib/commands/recycling.ts` (`recycleChunk`), `lib/domain/recycleMutations.ts` (`archiveRound`).

**Evidence.** Per recycled contact `archiveRound` issues, sequentially inside the transaction: 1 `INSERT` (archive),
5 child `UPDATE`s, 1 live-row `UPDATE` = 7 round trips, plus ~6 per chunk. A chunk is 100 contacts in one
`withLockTx` with `timeout: 30_000`. Measured with `.claude/r02-perf.ts` (fixtures, dev copy, cleaned up):

| Chunk | Measured locally (DB round trip 20.8 ms median) | Estimate, functions in Neon's region (~2 ms) | Estimate, Vercel `iad1` → Neon `eu-central-1` (~90 ms) |
|---|---|---|---|
| 10 contacts | 1.7 s | ~0.2 s | ~7 s |
| 100 contacts | **14.9 s** (149 ms / contact) | ~1.5 s | **~64 s > 30 s timeout** |

The time is almost entirely latency (149 ms per contact ≈ 7 × 21 ms). The runbook (A7a) already records that a
500-contact local run exceeded 60 s. Nothing in the repo records which Vercel region the functions run in (no
`vercel.json`, no `.vercel/`), and Vercel's default for new projects is a US region.

**Impact.** If the region is far from Neon: every chunk hits the transaction timeout, rolls back, and the admin gets
"Skúsiť znova" forever — the feature does not work at all, on the day it is needed. Lock time per chunk (up to 30 s
holding row locks on 100 contacts and `FOR SHARE` on their callers) also blocks those callers' saves for that time.

**Required fix.**

1. **Before rollout:** verify the production function region (Vercel → Project → Settings → Functions → Region) and
   record it in `production-rollout.md`. If it is not `fra1` (Frankfurt, same as Neon `eu-central-1`), do not roll
   out without (2).
2. **Make the write set-based** so a chunk costs a constant number of statements: generate the archive ids in code,
   insert all archive rows with one `INSERT … SELECT` (or `createMany`) from the locked live rows, re-point each child
   table with one `UPDATE … FROM unnest($live_ids, $archive_ids)`, reset all live rows with one `UPDATE … WHERE id =
   ANY(...)` (one bump each). ~10 statements per chunk regardless of size. Keep the per-row re-validation as today.
3. Until (2) lands, a smaller `CHUNK` (e.g. 25) is a cheap mitigation that keeps each transaction well inside 30 s even
   at ~90 ms.

**Tests to add.** A budget test in `check-concurrency.ts`: recycle 100 contacts and assert the number of statements
per chunk is constant (count via a Prisma query event or wrap `tx`), and record the duration; plus the existing
partial-commit / retry tests unchanged.

### R02-02 — P2 — admins and managers cannot edit or delete a recycled contact from Kontakty (regression)

**Where:** `lib/queries/contacts/index.ts` (`editable`), `app/dashboard/contacts/page.tsx` (`locked={!row.editable}`),
server `lib/actions/contacts/index.ts` (`lockContactForManage`).

**Evidence.** `editable = round === 1 && NEW && unclaimed && no CALL` is computed without knowing the viewer and used as
the UI lock for everyone. The server returns early for `contacts.deleteAny` (managers, admins) and allows them any
edit. Before Feature 02 the lock was `!callable`, so an admin could edit an unclaimed NEW contact. In the browser as
`michal` (ADMIN), every recycled row in Kontakty shows the lock "obvolaný" and no pencil.

**Impact.** The "Zlé číslo" bucket is recyclable (with a warning that the caller gets the same number), but nobody can
correct the number in the UI before the contact is claimed: not the admin (UI lock), not the scout (correctly locked).
The same applies to any data fix on the ~2 000 contacts about to be recycled.

**Required fix.** Lock per viewer, mirroring the server: viewers with `contacts.deleteAny` are never locked on a
non-deleted contact; others use `editable`. Pass a `canManageAll` flag from the page (from `can(viewer,
"contacts.deleteAny")`) rather than adding viewer logic to the row mapper.

**Tests to add.** HTTP render as an admin: a recycled row shows the edit action; as the scout who added it: locked
(existing `rc7Scout` covers the read model only).

### R02-03 — P2 — Na volanie shows a list position, not the queue position

**Where:** `app/dashboard/contacts/page.tsx` (`index + 1`), `lib/queries/contacts/index.ts` (pool view).

**Evidence.** Spec §15.2: "in Na volanie the first column is the **position in the queue**"; the page subtitle says
"V poradí, v akom ich dostane volajúci". The number is the row index of the *filtered* list. Browser, as admin,
`?view=pool&round=2`: the pool holds 243 contacts, 40 of them fresh ones ahead of every recycled one, yet the first
recycled contact (#4) is labelled "1." — the next "Vziať ďalších 10" will not take it. The same happens with the scout
scope (a scout sees "1." for their first waiting contact), a team / creator filter, or a search.

**Impact.** Michal reads "1." as "called next" and plans around it; it is wrong as soon as any filter is used.

**Required fix.** Compute the global rank in SQL — `row_number() OVER (ORDER BY ${POOL_ORDER_SQL})` over the whole
`POOL_WHERE` set — then apply scope / filters / round and return that rank with each row. (Alternative: show the
position only when no filter is active; worse.)

**Tests to add.** KV-3: with fresh contacts ahead and `round=2`, the first recycled row carries rank = number of
contacts ahead + 1; a scout's first row carries its global rank.

### R02-04 — P2 (workflow) — no protection for contacts who asked not to be called again

**Where:** spec §5 / §8; `getRecycleList`.

**Evidence.** `call_lost` (2 061 on the copy, default-selected) is "Nemajú záujem" from the first call. That outcome
covers both "not now" and "never call us again". The app stores the difference only as free text in `Lead.note`
(which a first call may overwrite) — there is no flag. The recycle panel never shows `note` for call-stage contacts
(only the outcome; `lostReason` only for deals) and cannot search or filter by it. Recycling keeps the note
(Q2), so the caller sees "nevolať!" only after dialling.

**Impact.** Bulk recycling re-calls people who explicitly refused further contact: complaints, reputational and
possibly legal exposure for cold calls, and wasted caller time. Michal's stated worry (callers being blindsided) is
the same class of problem.

**Required decision / fix (Michal).** At minimum: show the note in the panel (a column or a tooltip) and include it in
the panel search, so contacts with "nevolať" / "nevolajte" can be found and left out. Better: a default exclusion of
contacts whose note matches a short do-not-call word list, shown as its own count. A real "nevolať" flag is a later
feature.

### R02-05 — P3 — recycling an active caller's work gives no warning

The confirmation lists owners only for open deals (`summarizeRecycleSelection` → `owners`). Recycling `call_retry`,
`call_scheduled` or `call_snoozed` contacts held by an **active** caller (on the copy: jurcovam 52 retries, michal 1)
silently removes them from that caller's "Opakovať" / callbacks with no notice. For timea (leaving) this is intended;
for an active caller it is not obvious. Spec §8 does not list it either (spec gap). **Fix:** add per-holder counts for
call buckets when the holder is active ("Miriam Jurčová: 52 z jej fronty"). Test: the summary pure function.

### R02-06 — P3 — header number and its link disagree

`app/dashboard/contacts/page.tsx`: "N voľných na volanie" is `getContactsOverview().callable` (scope only) but links

### R02-07 — P3 — "obvolaný" lock label on recycled contacts

`ContactRowActions` shows "obvolaný" (tooltip "Kontakt je už obvolaný") for every locked row. A recycled contact is
locked because it is not the scout's anymore, not because it was called in this round. **Fix:** a reason-specific
label ("recyklovaný") or tooltip; trivial once R02-02 passes the lock reason.

### R02-08 — P3 — order inside one recycle batch

`archiveRound` gives every contact of a chunk the same `roundStartedAt` (`new Date()` once per chunk), so the queue
order within a batch falls back to `id` (cuid ≈ original creation order) — not the order the admin selected (e.g.
"Posledný kontakt – najstaršie"). Browser: three contacts recycled together landed at 201–203 in id order. **Fix
(optional):** pass the selection order and set `roundStartedAt = now + i ms`, or document that a batch keeps creation
order.

### R02-09 — P3 — archive rows consume `#number`

Every archive row takes the next `Lead.number`. After recycling 2 000 contacts the next scouted contact's number jumps
by 2 000 (the dev copy is already at #18 8xx from test fixtures). Not harmful — `number` is an identifier, not a count —
but visible to the team and not mentioned in the spec (§4.3 says only "hidden"). **Fix:** document it; if unwanted,
archive rows would need their own numbering, which is a schema change — not recommended for v1.

## What was checked and is correct

- **Schema:** dev DB = `schema.prisma` (empty `migrate diff`); `sql/01-recycling-schema.sql` byte-identical to a fresh
  `migrate diff` from `origin/main`'s schema; additive only; old code compatible; generated client built on deploy
  (`build` runs `prisma generate`, `app/generated` not committed).
- **Archive integrity:** every `Lead` column copied or explicitly excepted (`rc1Snapshot`); all five child tables move,
  nested rows follow; archive recompute is a no-op; live row equals the fresh-contact shape; one revision bump.
- **Invisibility:** guards, pool, board, pipeline, inbox, História, deactivation, contacts, stats (contacts added),
  call history links — code + tests.
- **Idempotency:** a replay of a pre-recycle call key against the recycled contact returns `IDEMPOTENCY_CONFLICT`
  (`idempotentReplay` compares `leadId`), as spec §4.4 claims; a repeated recycle request counts as already recycled,
  never a second round (two concurrent identical requests → one archive per contact).
- **Concurrency:** lock order users `FOR SHARE` (ascending) → leads `FOR UPDATE ORDER BY id`; analysed against
  `claimBatchAs`, `transferCallWorkAs` (users `FOR UPDATE` first), `changeOwnerAs`, `logCallAs`, deactivation — no
  lock-order inversion; forced races in both orders have exactly one winner (tests).
- **Tracking:** ingest checks only `design.deletedAt`, so an old návrh link keeps recording onto the archived round.
- **Permissions:** page and command require `contacts.recycle` (ADMIN only); MANAGER refused (test + browser
  redirect); `pickRecycleFirst` checks it too.
- **Caller UI:** the call board renders "#56 jural.sk **2. kolo**" for a recycled contact in a batch
  (`.claude/r02-callboard.ts`, throwaway caller).
